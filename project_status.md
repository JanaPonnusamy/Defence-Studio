## F1 implementation notes

F1 added a standalone Python/FastAPI package under `backend/defence_studio`; it does not import QVault or Whisper Studio. SQLite is authoritative at `DEFENCE_STUDIO_DB_PATH` (default `data/defence_studio.sqlite3` under the project root). Bootstrap creates schema version 1 with additive `CREATE TABLE IF NOT EXISTS` statements, WAL mode, foreign keys, and bounded busy timeout. Unsupported schema versions fail closed. No prior Defence Studio application database existed to migrate.

The API derives `owner_id` from a verified HS256 bearer token. Configure a random `DEFENCE_STUDIO_AUTH_SECRET` of at least 32 bytes and an external trusted token issuer. F1 does not issue tokens or register users. Job creation is idempotent by `(owner_id, Idempotency-Key)` and a canonical payload digest. SQLite `BEGIN IMMEDIATE` plus a unique constraint serializes concurrent duplicates. The thirteen persisted stages preserve the design pipeline order; stage execution cannot begin until its predecessor is completed or skipped. Transition history stores UTC times/errors. Artifact references are append-only versioned rows scoped to `jobs/<job_id>/` with a schema version and caller-supplied SHA-256.

F1 itself did not include a worker. F2 adds an opt-in durable worker engine and startup recovery while keeping the API worker loop and all production handlers disabled. No feed provider, download, AI service, rendering, artifact byte store/checksum verification, full auth integration, or Phase 1 execution is enabled. See `backend/WORKER_CONTRACT.md` for the F2 guarantees and limits.

## F3 implementation and verification

F3 adds a content-acquisition engine (`defence_studio.acquisition`) plus a path-safe artifact byte store (`defence_studio.storage.artifacts`), running only as the handler registered for the locked `topic_search_and_source_collection` worker stage — no HTTP endpoint, no synchronous execution. It acquires real bytes for explicit, already-approved targets (http(s) pages/PDFs and YouTube subtitles/captions only, never full video) through an SSRF-guarded fetcher (`url_guard.py`/`http_client.py`) that blocks loopback/private/link-local/reserved addresses on every resolved address and every redirect hop. Declared, source-supplied metadata is preserved with an explicit `COLLECTED`/`UNAVAILABLE`/`NOT_COLLECTED` status per field — nothing is fabricated. Acquisition is idempotent (hash-verified reuse of already-stored sources, including across a worker retry after a simulated crash) and reports explicit partial success across multiple targets; one target's failure never substitutes a different source. Full field-level contract in `backend/CONTRACTS.md`; QVault components inspected/adapted and those deliberately not reused are in `backend/SOURCE_PROVENANCE.md`. Implementation review remains the release gate before Phase 1A/1D or any downstream phase.

## F4 implementation and verification

F4 adds a deterministic, stdlib-only analysis layer (`defence_studio.analysis` + `defence_studio.contracts.analysis`) running only as the handler registered for the locked `extraction_validation_normalization_deduplication` worker stage — no HTTP endpoint, no AI/paid-API call. It reads F3's real `acquisition_manifest` artifact, independently re-verifies each referenced byte artifact's SHA-256 before trusting it, normalizes HTML/subtitle/plain text without stripping qualifiers/negations/dates/units/designations, deduplicates sources (same-URL, identical-content, and threshold-based near-duplicate text) while preserving every original source record, extracts verbatim claim spans with exact offsets (never a paraphrase, never asserted as true), flags cross-source conflicts for human review without merging either side, and writes one versioned, content-addressed `analysis_result` artifact. A strict schema-validation seam (`ai_schema.py`) exists for a future AI-assisted extractor but is not wired to any provider in this phase. Full field-level contract in `backend/CONTRACTS.md`; no QVault/Whisper Studio source was reused (`backend/SOURCE_PROVENANCE.md` F4 section). Implementation review remains the release gate before Phase 1D or any downstream phase.

During implementation, two real bugs were found and fixed before marking F4 complete, not just test bugs papered over: (1) a test-fixture helper was double-writing bytes for an "ACQUIRED" source even when the test intended to override its artifact list afterward, silently replacing a deliberately-deleted/corrupted file and collapsing an intended `ARTIFACT_UNREADABLE` case into `ARTIFACT_CORRUPT` — fixed in the test, not the service. (2) a genuine service bug: `run_and_store`'s content-addressed output path was keyed by input identity, but the serialized artifact still embedded a wall-clock `analysis_timestamp`, so two runs over byte-identical inputs produced different file contents (and therefore different SHA-256) at the same path — contradicting the claimed idempotency guarantee. Fixed by adding a check-before-write short-circuit: if an artifact already exists at the computed input-digest path, it is reused as-is rather than rewritten, mirroring the check-before-reuse pattern F3 already uses for its own idempotent re-acquisition.

F3 landed as real, complete code (not a placeholder) partway through this session — `defence_studio.acquisition` with `http_page`/`youtube_subtitles` providers, `build_acquisition_handler`, and its own passing test suite — so F4 was wired against the actual F3 output contract rather than a guessed one. Two concrete mismatches were caught and corrected during wiring: the real F3 manifest artifact type is `acquisition_manifest` (not the `acquisition_result` initially assumed before F3 landed), and real per-source byte artifacts are typed `source_content`/`source_subtitles` with schema `defence-studio.source-artifact.v1` (not `raw_page`/`raw.v1`). `ACQUISITION_RESULT_ARTIFACT` in `contracts/analysis.py` was corrected to match F3's real constant, and one end-to-end test (`test_real_f3_acquisition_output_feeds_real_f4_analysis_through_worker`) drives the actual `build_acquisition_handler` (via a mocked HTTP transport, no live network) and the actual F4 handler back-to-back through the same F2 `Worker`, proving the wiring against real F3 code rather than only a hand-built fixture.

It implements the full review workflow end to end — browse sources and claims, filter by status/conflict/source, inspect provenance/passages/entities/conflicting-claim pairs, approve/reject/request-more-evidence/mark-conflict-unresolved with a confirmation dialog and a required note field, see persisted reviewer/timestamp/revision and full history, and resume after a refresh via `localStorage`-persisted job ID and bearer token.
