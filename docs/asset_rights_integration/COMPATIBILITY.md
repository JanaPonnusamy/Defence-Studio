# Asset & Rights Engine (ARE 1.1.0) vs Defence Studio asset model — compatibility assessment

Phase 5C, Workstream A. Read-only comparison; no product code was changed to produce this
document.

**Sources compared**
- Standalone: `E:\DefenceStudio-Components\asset-rights-engine\src\asset_rights_engine\{contracts.py,engine.py,adapter_contracts.py,host_adapter.py}`, `docs/HOST_ADAPTER.md`, `CONTRACTS.md`, `A2_ACCEPTANCE_REPORT.md`. (Consolidated 2026-10-14 into `components/asset-rights-engine/` under the project root; historical path left as-is.)
- Defence Studio: `backend/defence_studio/contracts/assets.py` (M2.0), `backend/defence_studio/services/assets.py` (M2.1), `backend/defence_studio/database.py` (schema v7), `backend/defence_studio/api/app.py` asset routes.

The two systems were built independently against similar but not identical requirements.
**They are not drop-in compatible.** Any mapping below is explicit; nothing is assumed
equivalent just because the names look alike.

## Legend

- **Compatible** — same meaning, safe to treat as equivalent.
- **Adaptable** — different shape/vocabulary, but a deterministic, lossless (or explicitly
  lossy-and-declared) mapping exists.
- **Missing (DS)** — Defence Studio has no equivalent.
- **Missing (ARE)** — the standalone engine has no equivalent.
- **Decision required** — the two sides disagree on meaning or safety semantics; adopting
  either side silently would change behavior.

## 1. Asset descriptor fields

| Concern | ARE 1.1.0 (`AssetDescriptor`) | Defence Studio (`AssetDescriptorV1`) | Classification |
|---|---|---|---|
| Identity | `asset_id` (free identifier, caller-supplied, mutable naming scheme) | `asset_id` = SHA-256 digest of the id-less body (content-addressed, server-computed) | **Decision required** — DS asset IDs are not stable under a field edit (a new hash = a new asset); ARE asset IDs are caller-assigned and persist across edits. A host cannot pass a DS `asset_id` into ARE's `asset_id` as if they had the same lifecycle semantics. |
| Type vocabulary | `asset_type`: image/video/audio/graphic/other (5 values) | `kind`: image/footage/audio/music/graphic/map/document/other (8 values) | **Adaptable** — DS's `footage`/`music`/`map`/`document` have no ARE equivalent; mapping them to ARE's closest bucket (`video`, `audio`, `other`, `other`) is lossy and must be declared, not silently collapsed. |
| Content integrity | `sha256`/`mime_type`/`byte_size` optional, all-or-related-validated (MIME must match type for image/video/audio) | `content.status` (`REFERENCED_ONLY`/`MEASURED`/`UNAVAILABLE`) + `content_sha256`/`media_type`/`byte_size` present **only** when `MEASURED` | **Adaptable** — ARE has no explicit "not yet measured" state; absence of `sha256` in ARE is structurally indistinguishable from "we chose not to record it." DS's `REFERENCED_ONLY` must map to omitting ARE's hash fields entirely, never a placeholder hash. |
| Provenance | Single flat `provenance: str` + `original_source: str`, both required non-empty strings | `AssetProvenanceV1`: `source_url` (optional) / `documented_origin` (optional) / `source_title`, `creator`, `publisher` as `DeclaredText` (value + `MetadataFactStatus`) | **Decision required** — ARE *requires* non-empty provenance/original_source for every asset; DS explicitly allows a descriptor with **no** `source_url` and no `documented_origin` (it just forces `UNVERIFIED` rights downstream). Feeding a DS asset with no provenance into ARE's constructor would fail `AssetDescriptor.__post_init__`'s `require(...bool(v.strip())...)` check. A host adapter must either (a) refuse to register such an asset with ARE, or (b) synthesize a non-empty provenance string — which would misrepresent DS's honest "unknown" state as a declared fact. Neither is cost-free; this is a product decision, not a mapping bug. |
| Timestamps | `created_at`, `registered_at`, both required, `created_at <= registered_at` enforced | No descriptor-level creation/registration timestamp; `AssetProvenanceV1.acquired_at` is optional and separate from the service's own `created_at`/`updated_at` DB columns | **Missing (DS)** — DS does not require or validate a "created before registered" invariant at the contract level; it is implicit in the DB row's `created_at`. |
| Tags | `tags: tuple[str,...]` | No tag field | **Missing (DS)** |
| Review lifecycle on the descriptor | None — ARE's `AssetDescriptor` carries no review/approval state at all; review lives entirely in `RightsRecord.state` and assignment `state` | `review_status`: DRAFT/PENDING_REVIEW/APPROVED/REJECTED/RESTRICTED/EXPIRED, directly on the descriptor/row | **Decision required** — DS conflates "is this asset usable" into one `review_status` field that mixes rights review outcome and asset-level lifecycle; ARE keeps asset registration, rights state, and assignment state in three separate dataclasses. A host adapter must decide which of ARE's three states (or combination) a given DS `review_status` value corresponds to — there is no 1:1 field. |

## 2. Rights declarations and revision history

| Concern | ARE 1.1.0 (`RightsRecord`) | Defence Studio (`RightsRecordV1`) | Classification |
|---|---|---|---|
| Lifecycle states | `RightsState`: UNKNOWN/PENDING_REVIEW/APPROVED/REJECTED/EXPIRED/REVOKED (state lives *inside* the rights record itself, with "Persisted input APPROVED is rejected" — i.e. ARE enforces create-then-review as two separate steps at the data-model level) | DS's `RightsRecordV1` has **no state field at all** — the record is pure content (basis, licence, permissions, expiry); lifecycle is tracked separately via `AssetReviewStatus` on the asset row and `asset_reviews`/`asset_review_history` tables | **Decision required** — this is a structural difference, not a renaming. ARE's revision/state coupling (one `RevisionView` per rights entity, state transitions gated by `create_rights_revision`/`review_rights`) cannot be mapped field-for-field onto DS's split "immutable content row + separate review-decision row" design without picking one as authoritative. If ARE becomes the engine of record, DS's `asset_reviews` ledger becomes redundant with ARE's own review history — a real architectural choice (see Workstream D). |
| Basis vocabulary | `rights_basis: str \| None` — free string, not an enum, no "unknown" sentinel beyond `None` | `RightsBasis` enum incl. explicit `UNKNOWN` member (first-class, not absence) | **Adaptable** — DS's enum is strictly more expressive; `RightsBasis.UNKNOWN` maps to ARE's `rights_basis=None`, and any other DS value maps to the equivalent free string. Lossy in one direction only (ARE → DS: an arbitrary ARE string that isn't one of DS's 8 enum values has no DS target and must be rejected or bucketed, not guessed). |
| Commercial/modification/distribution permissions | Three independent tri-state Booleans (`commercial`, `modification`, `distribution`: `True`/`False`/`None`=unknown) | `commercial_use: CommercialUse` (allowed/prohibited/unknown) only; **no modification or distribution permission field exists in DS at all** | **Missing (DS)** — DS's `RightsRecordV1` cannot express "distribution not permitted" or "no derivative works" as a structured permission; it only has free-text `restrictions: list[str]`. This is a real gap, not a naming mismatch: ARE's `evaluate_effective_rights(..., UseContext(modification=True))` can refuse on a specific permission DS has no field for. |
| Expiry | `valid_from`/`valid_until` (interval, `valid_from < valid_until` enforced, `valid_until` is **exclusive** per ARE's own validation) | `expires_at` only (no `valid_from`); `_iso_is_past` treats a malformed or unparseable expiry as **expired** (fail-closed) | **Adaptable with a fail-closed difference worth flagging** — DS has no concept of "not yet valid" (an asset whose rights grant starts in the future); ARE does. Mapping DS → ARE: `valid_from=None`. Mapping ARE → DS: `valid_from` is silently dropped, which changes a real ARE semantic (a not-yet-active grant) into DS's "no constraint until expiry" semantic — this is a deliberate narrowing, not neutral. |
| Territory restriction | `territories: tuple[str,...]` of uppercase 2-letter codes, deduplicated/sorted; **empty = no restriction stated** (ARE's contract doc doesn't document the empty-means-what rule explicitly in the dataclass itself — only `UseContext.territory` single value is checked against it elsewhere) | `territory restrictions use uppercase two-letter codes; omission of a territory blocks a restricted grant. Empty territory list declares no territory restriction` (per DS `CONTRACTS.md`, M2.0 commentary) | **Compatible** — both use uppercase 2-letter codes with the same empty-list convention; format is directly portable. |
| Attribution | `attribution_required: bool\|None`, `attribution_text: str\|None` (no exact-match enforcement visible in the dataclass) | `attribution_required: bool` (no `None`), `attribution_text` with the **exact-match** requirement documented at the DS contract level ("required attribution must exactly match the declared text"), plus a structural rule rejecting `attribution_text` set when `attribution_required=False` | **Adaptable** — DS is strictly stricter (forbids a contradictory combination ARE would silently accept) and has no tri-state "unknown whether attribution is required." Mapping DS → ARE is safe; ARE → DS requires deciding what `attribution_required=None` becomes (DS has no `UNKNOWN` member for this field — only `True`/`False`). |
| Revision history | `create_rights_revision(asset_id, record, expected_revision)` → `RevisionView`; immutable per-revision, optimistic-concurrency via `expected_revision`; review via `review_rights(asset_id, ReviewRequest)` → `ReviewEvent`, queryable via `get_review_history()` | Immutable `asset_rights` rows keyed `(job_id, asset_id, rights_sha256)` (content-addressed, not a monotonic revision counter) + separate `asset_reviews`/`asset_review_history` (current + append-only, reviewer/decision/note/digest-pinned) | **Adaptable** — both are immutable-revision + append-only-audit designs, but DS keys rights revisions by content hash while ARE keys by a monotonic integer revision tied to `expected_revision` optimistic locking. A host adapter translating DS rights changes into ARE `create_rights_revision` calls must synthesize/track the `expected_revision` sequence itself; it does not exist natively in DS's hash-keyed model. |

## 3. Effective-rights evaluation

| Concern | ARE 1.1.0 | Defence Studio | Classification |
|---|---|---|---|
| Entry point | `Engine.evaluate_effective_rights(asset_id, UseContext)` — stateful, reads the engine's own persisted rights history; separately, a documented **pure** evaluator function exists but "for an untrusted caller always use `Engine.evaluate_effective_rights`" | `evaluate_effective_rights(rights, provenance, now_iso=..., for_commercial=..., target_use=...)` — pure function, no I/O, caller supplies everything including the clock | **Adaptable** — DS's function is ARE's "pure evaluator" shape, not ARE's stateful `Engine` method. If ARE becomes the rights engine of record, DS's own `_derive_effective_rights` call sites in `services/assets.py` would need to be replaced by calls into `Engine.evaluate_effective_rights`, not merely wrapped — the pure DS function doesn't consult a persisted review history the way ARE's stateful method does. |
| Output shape | `Evaluation`: `eligible: bool`, `blockers: tuple[str,...]`, `warnings: tuple[str,...]`, `review_actions: tuple[str,...]`, `rights_revision`, `rights_hash`, `evaluated_at` | `EffectiveRights` enum: CLEAR/RESTRICTED/UNVERIFIED/EXPIRED/BLOCKED (a single verdict, no blocker list) | **Decision required** — ARE returns a structured list of blocker/warning *codes*; DS collapses everything into one enum value. DS's `assignment_readiness()` separately builds its own ad-hoc blocker strings (e.g. `"asset {aid}: effective rights {X} (not CLEAR)"`) that are **not** the same thing as ARE's `Evaluation.blockers` — they're assembled by DS service code, not returned by the rights evaluator itself. Unifying these would require deciding whether DS's readiness blockers become a consumer of ARE's `Evaluation.blockers`/`warnings`, replacing DS's own string-building. |
| Always-present warning | None documented as mandatory | ARE: "Readiness always warns `MEDIA_AVAILABILITY_UNVERIFIED`; it is rights readiness, not render readiness" | **Compatible in spirit, absent in DS** — DS's `review_asset`/`assignment_readiness` carry an equivalent honesty principle (asset bytes are never asserted as fetched; `REFERENCED_ONLY` is explicit) but do not emit a parallel structured warning code. **Missing (DS)** as a literal field. |
| Fail-closed rules | Unknown/missing → defaults to blocked without review evidence (pure evaluator); expiry, commercial/non-commercial, territory, permission flags all individually checked | Unknown basis/commercial-use/missing provenance → `UNVERIFIED`; `cc_by_nc`/prohibited (commercial) → `BLOCKED`; past/malformed expiry → `EXPIRED`; target-use outside permitted → `RESTRICTED`; else `CLEAR` | **Compatible in philosophy** (both fail closed on unknown), **not compatible in granularity** — DS has 5 coarse verdicts; ARE has a boolean `eligible` plus an open list of blocker codes. A verdict of DS `RESTRICTED` could correspond to many different ARE blocker combinations; collapsing ARE's blocker list down to one DS enum value loses information DS's own UI/readiness output currently surfaces as free text, not structured codes. |

## 4. Assignment identifiers and scene bindings

| Concern | ARE 1.1.0 (`AssignmentDescriptor`/`SceneBinding`) | Defence Studio (`AssetAssignmentV1`) | Classification |
|---|---|---|---|
| Binding identity fields | `SceneBinding{host_application, job_id, scene_id, plan_version: str, plan_sha256, content_digest?}` | `AssetAssignmentV1{job_id, language, version, scene_plan_sha256, scene_plan_version: int, scene_id, asset_id, effective_rights, target_use?, created_at}` | **Adaptable** — DS has no `host_application` field (single-tenant-per-DB assumption, see §7); ARE's `plan_version` is a **string** (ARE-A2's own host-adapter doc notes: "This adapter contract deliberately uses integer plan revisions; ARE-A1 still accepts opaque plan-version identifiers" — i.e. ARE-A1's core is string-typed, ARE-A2's host layer narrows it to a positive integer) while DS's `scene_plan_version` is natively an `int`. DS → ARE: `str(scene_plan_version)`. ARE → DS: only safe if the ARE string is itself a positive base-10 integer; an opaque non-numeric ARE plan_version has no DS representation. |
| Assignment identity | `assignment_id` is a caller-supplied free identifier, independent of asset_id, passed into `create_assignment(assignment_id, asset_id, binding, ...)` | No standalone `assignment_id` — DS assignments are addressed by the composite `(job_id, language, scene_id, asset_id, version)`; `assignment_sha256` is a content digest, not an identity | **Missing (DS)** — there is no DS field that plays the role of ARE's caller-assigned `assignment_id`. A host adapter would have to invent one (e.g. derive it from the composite key) since ARE's API requires it as an explicit parameter. |
| Role | `role: str` (free identifier, e.g. "primary-visual") | No equivalent — DS has `target_use: PermittedUse | None` (broadcast/web/derivative/thumbnail), which is a *use* classification, not a *role* classification | **Decision required** — `role` and `target_use` are not the same axis (one asset could have one role but multiple valid target uses). Mapping one into the other conflates two different concerns from the DS side. |
| Multiple assignments of the same asset to the same scene | ARE: a given `assignment_id` is one entity; nothing in the contract snippet shown prevents multiple distinct `assignment_id`s pointing at the same `(asset_id, binding)` | DS: `version = MAX(version)+1` **per `(job_id, language, scene_id, asset_id)`** — i.e. re-assigning the same asset to the same scene creates a new version of *that exact tuple*, and a prior ACTIVE row for that tuple is superseded (`status='REMOVED'`) | **Adaptable**, but the supersession rule is DS-specific business logic with no ARE equivalent to inherit — it must be preserved by the host layer, not assumed to come from ARE. |
| Stale-plan detection | `evaluate_assignment_readiness` yields `STALE_SCENE_BINDING` "without silently rebinding assignments" when the authoritative plan binding changes | DS: `list_assignments()` computes `stale_plan: bool` by comparing `scene_plan_sha256` against the job's *current* approved plan each read — not stored, recomputed live | **Compatible in philosophy** (both detect staleness without auto-rebinding), **different mechanism** — ARE's staleness is engine-evaluated per the host's asserted `HostSceneContext`; DS's is a plain SQL comparison against its own `scene_plans` table. If ARE becomes authoritative, DS's `scene_plans` table would no longer be the source of truth for staleness detection — a real behavior change, not a renaming. |

## 5. Approved scene-plan revision and digest

| Concern | ARE 1.1.0 (via `adapter_contracts.HostSceneContext`) | Defence Studio (`scene_plans` + M1 `SceneService`) | Classification |
|---|---|---|---|
| Plan revision type | `plan_revision: positive int` (ARE-A2 host contract) | `scene_plan_version: int`, `plan_sha256` | **Compatible** — both are positive integers plus a lowercase-hex SHA-256; this is the one area with a near-exact type match. |
| Approval assertion | `host_asserts_approved: bool`, validated to be consistent with `PlanState` (`APPROVED` state requires the Boolean true; contradictory combinations rejected at DTO construction) | `scene_plans.status = 'APPROVED'` row lookup (`_current_approved_plan`); no separate redundant Boolean | **Compatible in effect** — both ultimately gate on "is this plan currently approved," but ARE's host contract explicitly distrusts a bare Boolean ("even a matching scope is not proof of authority" — see HOST_ADAPTER.md "Three distinct trust levels") whereas DS currently has **no host-boundary concept at all**: `AssetService.assign_asset` trusts its own DB row directly, which is correct *because* DS has no external host layer yet. If ARE's host-asserted model were adopted, DS's direct DB truth would need to become the thing that *populates* the asserted `HostSceneContext`, not be replaced by it. |
| Staleness after re-approval | `STALE_PLAN`/`STALE_SCENE_BINDING` error codes, explicit | DS's own `AssetStaleRevision` (409) at assignment time if no approved plan exists; `stale_plan` flag at read time if the plan changed after assignment | **Compatible** in intent, different granularity — ARE distinguishes "plan is stale" from "scene binding stale" as two codes; DS uses one boolean flag plus one exception type. |

## 6. Review decisions and review history

| Concern | ARE 1.1.0 (`ReviewRequest`/`ReviewEvent`) | Defence Studio (`asset_reviews`/`asset_review_history`) | Classification |
|---|---|---|---|
| Reviewer identity | `reviewer: str` — a field on the request object itself, validated as an "identifier" (ASCII pattern) but **not inherently tied to an authenticated session** at the ARE core level; ARE-A2's host-adapter layer adds the requirement that `request.reviewer == principal.principal_id`, explicitly enforced by `AdapterGateway`, not by core `Engine.review_rights` | `owner_id` passed as a function parameter to `review_asset(...)`, sourced server-side from `Depends(require_owner)` in `api/app.py` — the HTTP layer, not the caller's request body | **Compatible in outcome, different enforcement point.** Both end up requiring reviewer identity to come from something other than a client-supplied field, but DS enforces it at the API-route dependency layer (no reviewer field exists in `AssetReviewBody` at all — see Workstream C), while ARE's *core* `Engine.review_rights` would accept whatever `reviewer` string is in the `ReviewRequest` unless wrapped by the ARE-A2 `AdapterGateway`. If Defence Studio called `Engine.review_rights` directly (bypassing the gateway), it would have to independently ensure the `reviewer` field it constructs is always exactly the authenticated `owner_id` — the core engine does not enforce that by itself. |
| Decision vocabulary | `decision: "APPROVED" \| "REJECTED"` only (2 values) | `decision` in `{APPROVED, REJECTED, RESTRICTED, CHANGES_REQUESTED}` (4 values) | **Missing (ARE)** — ARE's core review decision has no equivalent to DS's `RESTRICTED` (conditionally usable) or `CHANGES_REQUESTED` (send back for correction without a terminal rejection). Mapping DS → ARE loses information unless the host layer tracks these DS-only states outside ARE's `ReviewEvent`. |
| Idempotency key scope | `idempotency_key` unique **across all review kinds** (rights + assignment reviews share one keyspace per ARE's `CONTRACTS.md`) | `idempotency_key` scoped per-call-site: `(job_id, asset_id, reviewer_id, idempotency_key)` unique in `asset_review_history`; a separate `register_asset`/`assign_asset` idempotency scope entirely | **Adaptable** — both are idempotent-replay designs; the keyspace partitioning differs and a host adapter must not assume a DS idempotency key is safe to reuse across ARE's wider shared keyspace without re-scoping it. |
| First-decision-wins / concurrency | "First decision per entity revision wins; additional decisions require a new revision" + documented unspecified race-winner identity under concurrent opposite decisions | DS: `expected_revision` optimistic-concurrency check inside `BEGIN IMMEDIATE`; a losing concurrent call gets `AssetRevisionConflict` (409), explicit winner is whichever transaction commits first (SQLite serializes) | **Compatible** — both are optimistic-concurrency, first-committer-wins designs with an explicit conflict signal rather than silent overwrite. |
| Readable history | `get_review_history()` returns all `ReviewEvent`s for the whole engine instance (not filtered to one entity in the snippet shown) | `asset_review_history(job_id, owner_id, asset_id)` — scoped to one asset, with the service itself enforcing job ownership before returning rows | **Decision required** — ARE's `get_review_history()` as shown returns engine-wide history; if ARE is given one SQLite file per Defence Studio job/tenant (see Workstream D), this is equivalent to DS's per-job scoping only *because of* storage-level isolation, not because the API itself takes a job/asset filter. If ARE's engine is shared across multiple DS jobs, `get_review_history()` would leak cross-job data unless filtered by the host layer. |

## 7. Ownership and tenant boundaries

| Concern | ARE 1.1.0 | Defence Studio | Classification |
|---|---|---|---|
| Core engine | **No tenant/owner concept at all.** `Engine` operates on one SQLite file with no owner/tenant column anywhere in `contracts.py`/`engine.py`. Confirmed by `CONTRACTS.md`/`HOST_ADAPTER.md`: "No implicit tenant isolation is added to Engine" and "equal job/scene IDs in another tenant do not imply shared identity." | Owner/job scoping is enforced on **every** `AssetService` method via `_check_ownership`/`_check_ownership_locked` against `workflow_jobs.owner_id`, inside the same transaction as any mutation. | **Missing (ARE core).** This is the most important finding of this assessment: **ARE 1.1.0 provides zero tenant isolation by itself.** The ARE-A2 host-adapter layer (`HostScope`, `HostSceneKey`) exists specifically to let a *host* supply tenant/owner scope externally, but it is explicit that these "are host authorization scope, not new SQLite columns... not encoded into ARE-A1 scene IDs... Use trusted resource mappings and dedicated engines/storage per scope." |
| Isolation mechanism if integrated | ARE-A2's documented production prerequisite: "dedicated engines/storage per scope" — i.e. **one ARE `Engine`/SQLite file per tenant (or per job)**, not a shared engine with row-level tenant filtering | One shared `defence_studio.sqlite3` file, all jobs/owners in the same tables, isolated entirely by `WHERE owner_id=?` / `WHERE job_id=?` query filters plus the ownership check | **Decision required** — this is the single largest architectural mismatch. Defence Studio's entire existing isolation model is row-level (shared DB, filtered queries). ARE's documented production model is file-level (isolated DB per scope). Adopting ARE as-is without either (a) giving it one SQLite file per DS job, which multiplies file/connection count significantly, or (b) wrapping it so DS's existing row-level model remains authoritative and ARE is used only as a stateless/pure evaluator, is an open product decision — see Workstream D's two options. |
| Reviewer/principal trust | `HostPrincipal` is "an identifier only, with no authenticated flag" — explicitly not proof of authentication | `owner_id` is the verified HS256 bearer-token subject, authenticated before any service call | **Compatible in requirement, not provided by ARE.** Both systems require the *host* to supply a real authenticated identity; ARE does not and cannot authenticate anyone itself, by design. |

## 8. Idempotency and optimistic concurrency

| Concern | ARE 1.1.0 | Defence Studio | Classification |
|---|---|---|---|
| Registration idempotency | Not documented as idempotent in the reviewed contract — `register_asset(asset: AssetDescriptor)` takes a caller-supplied `asset_id`; nothing shown deduplicates by content | `register_asset` is both idempotency-key-replay-safe **and** content-addressed dedup (two different descriptors with the same key replay; two identical descriptors under different keys collapse to the same row) | **Missing (ARE)** — ARE's registration has no documented content-dedup or idempotency-key replay; a host adapter wanting DS's current guarantee would have to add it itself, not inherit it from ARE. |
| Rights/assignment concurrency | `expected_revision` parameter on `create_rights_revision`/`revise_assignment`; conflict raises `DomainError` | `expected_revision` parameter on `review_asset` (reviews only — `set_rights`/`assign_asset` are append/supersede operations without an `expected_revision` parameter) | **Adaptable** — the concept and mechanism (expected-revision optimistic lock) match for review operations. DS does **not** apply the same expected-revision discipline to `set_rights` (any owner call always succeeds and supersedes) — this is a genuine DS design choice (rights content is append-only by hash, not revision-numbered) that would need to be reconciled if ARE's revision-numbered rights model becomes authoritative. |
| Transaction boundary | Not shown in the reviewed snippet whether `Engine` methods use SQLite transactions internally; `_connection(write=False)` suggests per-call connections | DS wraps every multi-statement mutation in one `BEGIN IMMEDIATE` ... `commit()`/`rollback()` block, with the ownership re-check repeated **inside** the lock (`_check_ownership_locked`) to close a TOCTOU window between the initial check and the write | **Requires integration testing** — cannot be confirmed as compatible or incompatible from the contract/doc level alone; this must be verified by reading `engine.py`'s actual transaction handling (out of scope for this read-only comparison beyond what `engine.py`'s method list shows) before any integration. |

## 9. Readiness blockers

Already covered under §3 (effective-rights evaluation) — DS's `assignment_readiness()` builds
its own free-text blocker strings per scene (`"no asset assigned"`, `"effective rights {X} (not
CLEAR)"`, `"rights not APPROVED"`, `"STALE_PLAN"`) which are DS service-layer constructions, not
derived from ARE's `Evaluation.blockers`/`warnings`. **Classification: Decision required** — if
ARE becomes the rights engine of record, DS's readiness blocker text would need to be rebuilt
from ARE's structured blocker/warning codes rather than DS's own ad-hoc strings, to avoid two
divergent "why isn't this ready" explanations.

## 11. Error handling and public API compatibility

| Concern | ARE 1.1.0 | Defence Studio |
|---|---|---|
| Error type | Single `DomainError(code: str, message: str)` for all validation failures — no HTTP status mapping in the core (ARE has no HTTP layer at all) | `ReviewError` family (`ReviewNotFound`→404, `ReviewValidationError`→422, `StaleRevision`/`RevisionConflict`→409), each with a `status_code` class attribute consumed by one shared FastAPI exception handler |
| Additional host-layer error codes | `PLAN_NOT_APPROVED`, `STALE_PLAN`, `SCENE_MISMATCH`, `SCOPE_MISMATCH`, `RESOURCE_MISMATCH`, `PRINCIPAL_MISMATCH`, `HOST_POLICY_DENIED` (ARE-A2 adapter layer only, as `DomainError` codes) | `AssetStaleRevision`/`AssetRevisionConflict`/`AssetValidationError`/`AssetNotFound`, all deriving from the existing `ReviewError` family (no new HTTP handler was added for M2.1) | **Adaptable** — a host adapter would need to translate ARE's `DomainError(code, ...)` into the matching DS exception subclass (e.g. `PLAN_NOT_APPROVED` → `AssetStaleRevision`, `SCOPE_MISMATCH`/`PRINCIPAL_MISMATCH` → a 403/404-class error DS doesn't currently have — DS's model is 404-for-cross-owner, not 403; see Workstream C). This mapping does not exist today and must be written, not assumed. |
| Public API shape | Python dataclass/function API only — no REST surface, no network protocol | FastAPI routes under `/api/jobs/{job_id}/assets/...`, `/scenes/{id}/assets`, `/assignments[/readiness]` | **Missing (ARE)** — ARE 1.1.0 ships no HTTP server at all (by design — see Option A vs B in `INTEGRATION_SPEC.md`); "public API compatibility" in the REST sense does not apply until a host exposes one. |

## 12. Readiness blockers vs ARE "production prerequisites"

ARE's own acceptance report lists, verbatim, what is **not** implemented and must come from a
host: "Real authentication, real host authorization, durable tenant mappings, proof of approval,
distributed transactions and media verification are intentionally unsupported." Every one of
these maps to something Defence Studio's *existing* F1–M2.1 code already does today (HS256
bearer auth, `_check_ownership`, SQLite `BEGIN IMMEDIATE` transactions) — **except** durable
multi-tenant mapping at the engine level, which DS also does not yet do in a way that would
satisfy ARE's "dedicated engine per scope" expectation (see §7). **Classification: Decision
required**, carried forward into `INTEGRATION_SPEC.md`.

## Summary of decision-required items (carried into Workstream D)

1. Asset identity model: DS content-addressed vs ARE caller-assigned IDs.
2. Provenance requiredness: ARE requires non-empty provenance; DS explicitly allows none.
3. Rights state ownership: DS splits content/review across two tables; ARE couples state into the rights record itself.
4. Missing DS permission axes: modification/distribution have no DS field.
5. Effective-rights output granularity: ARE's blocker-list `Evaluation` vs DS's single-enum verdict.
6. Role vs target-use: not the same axis; no safe automatic mapping.
7. Tenant isolation model: DS row-level-in-shared-DB vs ARE's documented per-scope-dedicated-engine.
8. Review decision vocabulary: DS's `RESTRICTED`/`CHANGES_REQUESTED` have no ARE equivalent.
9. Error/status-code mapping: no existing translation from ARE `DomainError` codes to DS's `ReviewError` family, including a DS gap around cross-owner responses that are 404 rather than 403 (see `SECURITY_REVIEW.md`).

None of these were resolved by this assessment; each requires an explicit product/security
decision before any real adapter is implemented.
