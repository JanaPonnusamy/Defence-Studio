# F2 durable worker contract

F2 adds persistent dispatch and stage claims to F1's owner-scoped job model. SQLite is the queue, claim ledger, retry schedule, transition history and artifact-reference authority. No feed, research, download, AI, rendering or other production stage handler is registered by F2.

## Job lifecycle

An owner can queue a new F1 `DRAFT` job whose stages are all `PENDING`. Repeating queue on a `QUEUED` job is idempotent; repeating it while an active worker claim exists returns the current `RUNNING` job without creating another claim. A manually `RUNNING` F1 job without a worker claim cannot be dispatched. `claim_next` moves the job to `RUNNING`, and each completed stage makes the job `QUEUED` if stages remain or `COMPLETED` when all stages are `COMPLETED`/`SKIPPED`. A failed attempt moves the stage to `FAILED` and job to `QUEUED` while retries remain; exhausting the stage limit makes the job `FAILED`. Terminal jobs cannot be queued or claimed. Existing F1 review states and transition rules remain in force; the worker only chooses the next ordered pending/failed stage and stops at `AWAITING_REVIEW`. Owner-driven transitions and artifact additions are rejected while that stage has an active claim, preventing manual writes from bypassing worker fencing.

## Claim lifecycle and atomicity

Each claim has a UUID `claim_id`, persisted `worker_id`, job/stage, attempt number, `ACTIVE` state, timestamps and lease expiry. It moves to `COMPLETED`, `FAILED`, or `EXPIRED`. `BEGIN IMMEDIATE` serializes claim acquisition and expiry recovery across processes; a partial unique index permits at most one active claim per job/stage. The candidate stage must be the first incomplete stage, its predecessor must be complete or skipped, its handler must be explicitly registered by that worker, its retry time must have arrived, and attempts must remain. Unexpired active claims cannot be taken over.

Every heartbeat, failure, and completion checks the exact claim ID, worker, job and stage and requires the lease still be valid. A stale worker therefore cannot commit after expiry or supersession. Heartbeat renewal and each result transaction are separately committed. Expiry is persisted before a replacement claim can be created. SQLite busy timeout is 30 seconds; callers should use one unique worker ID per worker process.

## Stage execution and artifact contract

Handlers receive immutable job/stage/claim context, the latest version of each artifact type from completed predecessor stages, a deterministic SHA-256 idempotency key derived from job, stage and those artifact identities, and a cancellation event. They return zero or more artifact references. The worker validates type/schema names, job-local relative URI and lowercase SHA-256 shape; stage completion, versioned artifact inserts, claim completion, transition history and job status update commit in one transaction. Artifact bytes are not written or checked by this layer.

Exactly-once execution of arbitrary external side effects is not promised. A handler that calls an external system must pass the context idempotency key to an idempotent API or reconcile the external result by that key before repeating the effect. A handler that cannot make effects idempotent or reconcile them must fail closed and must not be registered for automatic retry. This is enforced at worker construction: `Worker` requires that the set of registered handler stage keys exactly equals the `retry_safe_stages` set the host declares. A handler that is not declared retry-safe, a retry-safe declaration with no matching handler, or an empty handler map raises `ValueError` before the worker can run, so unclassified or unsafe stages cannot enter automatic retry execution. A process killed after an external effect but before SQLite commit may run the handler again after lease expiry. F2 contains no production handlers, so no external side effect is invoked.

## Lease, retry, recovery and shutdown

Default lease is 60 seconds (allowed range is over zero through 3600 seconds); the worker heartbeats every one-third of its lease, capped at 20 seconds and floored at 50 ms. Startup and every claim transaction recover all expired active claims. Recovery records the expired claim and error, transitions a running stage to `FAILED`, and either schedules exponential retry (1, 2, 4… seconds, capped at 60) or marks the job `FAILED` after the default three attempts. Attempts increment atomically on claim acquisition and survive restarts. Completed stages and artifact references are not changed by recovery. A handler receives cancellation if the heartbeat discovers lease loss; even if it ignores cancellation, its result is fenced from commit.

Graceful `shutdown()` stops new claims and lets the current handler finish; its lease heartbeat continues until the result commits. Abrupt process termination does not rely on cleanup: startup/next claim recovers only after lease expiry. API startup runs recovery, but does not start a worker loop. A host must explicitly instantiate a worker with explicit stage handlers. No handler registry/feed schedule is configured in this phase.

## Schema and F1 boundary

Schema version 2 migrates F1 version 1 additively in an exclusive transaction. It adds job `queued_at`; stage `attempt_count`, `max_attempts` (default 3), and `retry_after`; plus `worker_claims` and its active-stage uniqueness/expiry indexes. Existing F1 jobs, transitions and artifacts are retained. The schema version changes only at the end of the migration transaction. Versions other than supported v1/v2 fail before application-table DDL; there is no downgrade. F1 owner identity, token verification, `(owner_id, idempotency_key)` request identity, payload conflict behavior, ordered stages, authorization and append-only artifact versions are preserved. Queue is owner-scoped and workers receive no user token or cross-job user API. The worker cannot execute a manually running F1 stage without a persisted claim.
