# Defence Studio component contracts

F1 job and artifact contracts below remain in effect. F2 worker scheduling and recovery are defined in [`WORKER_CONTRACT.md`](WORKER_CONTRACT.md); its SQLite schema is version 2 and its API addition is `POST /api/jobs/{job_id}/queue`. F3 content acquisition is defined below under "F3 content acquisition contract" and runs only as a registered handler for the `topic_search_and_source_collection` worker stage. F4 source analysis is defined below under "F4 analysis contract" and runs only as a registered handler for the `extraction_validation_normalization_deduplication` worker stage. Phase 1A feed discovery is defined below under "Phase 1A feed discovery contract" and runs only as a registered handler for the `news_feed_and_topic_discovery` worker stage -- the predecessor to F3's stage. Phase 2 evidence-package/timeline/approval/export is defined below under "Phase 2 evidence-package, timeline, approval & export contract"; its SQLite schema is version 4 (`evidence_packages` ledger) and its API additions are `GET /api/jobs/{job_id}/timeline` and `GET|POST /api/jobs/{job_id}/package[...]`. Phase 3 source-grounded script generation/review/approval is defined below under "Phase 3 source-grounded script generation, validation, review & approval"; its SQLite schema is version 5 (`script_revisions` + `script_review_history`) and its API additions are under `GET|POST /api/jobs/{job_id}/script/...`.

## JobCreateV1 — `defence-studio.job-create.v1`

Purpose: persist the initial owner-scoped workflow request. Required fields: `topic` (trimmed, 1–1000 chars), `language` (trimmed, 1–1000 chars; API constrains to 2–20). Idempotency key is an HTTP header, 1–200 chars. Owner identity is derived from a verified HS256 bearer token's string `sub`, never from the request body. Output is JobStateV1, including stable UUID `job_id`, lifecycle status, ordered stages, and artifact references.

Validation: missing/oversize input → 422; no/invalid/expired token → 401; key reused for a different normalized request → 409. Same owner/key and same payload returns the original job. One `BEGIN IMMEDIATE` transaction plus UNIQUE(owner_id, idempotency_key) prevents duplicate rows under concurrent requests. Job creation persists the thirteen stage references from the locked design order; it does not schedule execution.

## Stage transition

Input: job ID, stage key, destination status, optional error up to 4000 characters. Statuses: PENDING, RUNNING, AWAITING_REVIEW, COMPLETED, FAILED, SKIPPED. From PENDING: RUNNING or SKIPPED. From RUNNING: AWAITING_REVIEW, COMPLETED, FAILED. From AWAITING_REVIEW: RUNNING, COMPLETED, FAILED. From FAILED: RUNNING. COMPLETED and SKIPPED are terminal. FAILED requires an error. A stage entering RUNNING or SKIPPED must have its predecessor COMPLETED or SKIPPED. Owner mismatch is intentionally indistinguishable from missing job (404).

Each valid transition increments the stage version and appends a transition record with UTC timestamp and error. The job updated timestamp and derived status persist in the same transaction. Invalid transition is 409; malformed status/error is 422. No worker side effect occurs.

## ArtifactReferenceV1 — `defence-studio.artifact-reference.v1`

Fields: artifact type, owning stage key, positive per-job/type version, relative URI under `jobs/<job_id>/`, lowercase SHA-256 digest, schema version, stable artifact ID and creation timestamp. The stage must have started. Each registration appends a version; prior versions remain addressable. Unknown stages, unsafe/out-of-job paths and invalid hashes are rejected. This boundary stores references and a claimed digest; it does not write files, verify bytes, or establish media rights.

## F1 persistence and failure behavior

SQLite is the only F1 authority. F1 initially used `schema_info` version 1 with foreign keys, WAL and 30-second busy timeout. F2 migrates it additively to version 2 for persistent scheduling, claims and recovery. Unsupported versions fail closed before application-table DDL. SQLite busy timeout/transactions bound ordinary contention. Unexpected database errors propagate as server errors; changes before commit roll back when the connection closes.

## HTTP endpoints

`POST /api/jobs`; `GET /api/jobs/{job_id}`; `POST /api/jobs/{job_id}/stages/{stage_key}/transitions`; `POST /api/jobs/{job_id}/artifacts`; and owner-authenticated `POST /api/jobs/{job_id}/queue`. All require a trusted issuer's HS256 token using the configured server secret, with `sub` and `exp`. Defence Studio does not mint tokens, register users, rotate/revoke tokens, or connect to an existing auth server. Components: `contracts/jobs.py`, `database.py`, `repositories/jobs.py`, `services/jobs.py`, `services/worker.py`, `auth.py`, `api/app.py`. Automated tests: `tests/test_workflow_jobs.py` and `tests/test_worker_engine.py`.

## F2 worker and claim contract

Only an owner can queue their new draft job; duplicate queue requests do not create another dispatch. Workers claim the first eligible stage in the locked order using SQLite `BEGIN IMMEDIATE` and a unique active-claim index. Claim IDs and worker IDs persist. Heartbeats and result commits are fenced by claim identity and an unexpired lease. Expired claims become failed attempts and retry after persisted exponential backoff until the three-attempt default is exhausted; exhaustion is terminal. Startup recovery runs with API lifespan startup. The API does not start a worker or register stage handlers. External side effects require stage idempotency keys or reconciliation; arbitrary exactly-once behavior is not claimed. Full lifecycle, schema, and shutdown rules are in `WORKER_CONTRACT.md`.

## F3 content acquisition contract

Purpose: acquire real source bytes for an approved research request and preserve traceable provenance, without starting extraction, verification, or any downstream phase. F3 runs only inside the F2 durable worker as the handler registered for the locked stage `topic_search_and_source_collection` (`defence_studio.contracts.acquisition.ACQUISITION_STAGE`); it has no HTTP endpoint and no synchronous execution path.

**AcquisitionRequestV1** (`defence-studio.acquisition-request.v1`, `defence_studio/contracts/acquisition.py`) — the stage's *input* artifact, produced by the predecessor stage and consumed from `context.input_artifacts` by `artifact_type == "acquisition_request"`. Fields: `job_id`; `targets` (non-empty list of `AcquisitionTarget`: `target_id`, `url`, `method` in `("auto","http_page","youtube_subtitles")`, `language_preferences`, optional `title_hint`); optional `project_id`; `limits` (`AcquisitionLimits`: `max_bytes_per_source`, `timeout_seconds`, `max_sources`, `max_redirects` — clamped server-side to hard ceilings in `acquisition/service.py`, never widened by the request). `defence_studio.contracts.acquisition.request_from_dict` parses and validates this; malformed input raises `RequestValidationError`, which the handler turns into a closed stage failure rather than guessing a default. If no `acquisition_request` exists yet, the handler builds targets from the predecessor `discovery_result` candidates (ranked order, capped by `max_sources`) and stores that derived request with `selection=automatic_from_discovery`. Zero fetchable URLs complete as a manifest with `requested=0` and a warning. An explicit request still wins over the full candidate list.

**AcquisitionResultV1** (`defence-studio.acquisition-result.v1`) — the stage's *output*, written as one JSON manifest artifact (`artifact_type = "acquisition_manifest"`, URI `jobs/<job_id>/research/acquisition_result.json`) referencing the hash of the exact bytes written. Carries `requested`/`succeeded`/`failed`/`skipped_duplicate` counts and one `AcquiredSourceV1` per target: `source_id` (stable SHA-256-derived dedup key over the canonical URL), `status` (`ACQUIRED`/`FAILED`/`SKIPPED_DUPLICATE`), `declared_metadata` (title/publisher/published_at/language, each paired with a `MetadataStatus` of `COLLECTED`/`UNAVAILABLE`/`NOT_COLLECTED` so "the source didn't supply this" is never conflated with "we didn't check"), `artifacts` (one `ArtifactRef` per stored file: type, relative URI, SHA-256 of the actual bytes, byte count, media type), `original_metadata` (raw provider-reported fields), `provenance` (provider name/version, source component, requested/canonical/final URL, acquisition timestamp, originating `target_id`), and on failure an `AcquisitionError` (`code`, `message`, `retryable`). A target never silently becomes a different source: failure is reported as `FAILED` with an honest error, not a substitution.

**Security boundary** — `defence_studio/acquisition/url_guard.py`'s `UrlGuard` rejects non-http(s) schemes, embedded credentials, and any URL whose host resolves to a loopback/private/link-local/reserved/multicast/unspecified address (including IPv4-mapped/6to4/Teredo IPv6 forms), blocking on *any* resolved address to defeat split-horizon DNS. `defence_studio/acquisition/http_client.py`'s `GuardedFetcher` re-validates every redirect hop through the same guard (closing redirect-to-SSRF), bounds redirects, streams the body with a hard byte ceiling enforced against both a declared `Content-Length` and the actual stream, and sends no cookies/Authorization/credential headers. Residual risk — DNS can change between validation and connect (TOCTOU) — is documented in that module's docstring, not claimed solved; full mitigation needs network egress controls around the worker host.

**Storage boundary** — `defence_studio/storage/artifacts.py`'s `ArtifactStore` is the only writer of acquisition bytes. Every URI must resolve under `jobs/<job_id>/...`, rejecting backslashes, absolute paths, `.`/`..` segments, and any resolved real path outside the job directory (defence-in-depth against symlink tricks). Writes are atomic (`tempfile` + `os.replace`) so an interrupted write never leaves a half-written file for a later SHA-256 to trust. `safe_filename` caps generated filenames at 80 characters with a content-hash fallback stem, avoiding the Windows `MAX_PATH` failures QVault's acquisition storage previously hit on long URL slugs.

**Providers** (`defence_studio/acquisition/providers/`) — `http_page` (generic `fallback=True` provider; downloads any http(s) page/PDF through the guarded fetcher, detects PDF-vs-HTML by content, and extracts only `<title>`/`og:site_name`/`article:published_time`/`html[lang]` as *declared* metadata — no article-body extraction, no OCR) and `youtube_subtitles` (host-restricted to YouTube domains; downloads *subtitles/captions only*, never the video stream, via an injectable yt-dlp backend that fails closed with a clear message if yt-dlp is not installed — the `youtube` extra is optional). `AcquisitionProvider.supports()`/`fallback` let `ProviderRegistry.resolve()` pick a provider under `method="auto"` by preferring any specific provider over a fallback; an explicit `method` pins one provider and raises `method_mismatch` rather than silently acquiring something else.

**Idempotency and reuse** — `AcquisitionService` derives `source_id` deterministically from the canonical URL, skips in-request duplicates as `SKIPPED_DUPLICATE`, and before any network call checks a per-source `acquired.json` sidecar; if its referenced artifact(s) still exist and hash-match, acquisition is skipped entirely and the prior artifacts are reused (verified in `test_acquisition_service.py::test_idempotent_reuse_avoids_redownload` and exercised across a real claim-expiry retry in `test_acquisition_handler.py::test_retry_through_worker_reuses_artifacts_without_redownload`). A handler re-run after a crashed attempt (lease expiry) therefore does not re-download.

**Partial success** — one target's failure never aborts the others; `AcquisitionResultV1.succeeded`/`failed`/`skipped_duplicate` and each source's own `status` make partial outcomes explicit rather than collapsing a multi-target request into one pass/fail.

**Tests**: `tests/test_url_guard.py`, `tests/test_artifact_store.py`, `tests/test_acquisition_service.py` (provider behavior via `httpx.MockTransport` and an injected yt-dlp double — the adapter boundary, not a live network claim), `tests/test_acquisition_handler.py` (full run through the real F2 `Worker`, a fail-closed missing-request case, retry-with-reuse across simulated lease expiry, and cross-owner artifact-read denial), and the opt-in, skipped-by-default `tests/test_integration_live.py` (real network; gated by `DEFENCE_STUDIO_LIVE_HTTP=1` / `DEFENCE_STUDIO_LIVE_YOUTUBE=1`).

## F4 analysis contract

Purpose: convert the real bytes F3 acquired into structured, traceable research material for the later human-review phase, without asserting that any extracted claim is true. F4 runs only inside the F2 durable worker as the handler registered for the locked stage `extraction_validation_normalization_deduplication` (`defence_studio.contracts.analysis.ANALYSIS_STAGE`); it has no HTTP endpoint. Its predecessor is `topic_search_and_source_collection` (F3), one ordinal earlier in the locked stage order.

**AnalysisRequestV1** (`defence-studio.analysis-request.v1`, `defence_studio/contracts/analysis.py`) — logical input shape: `job_id`, `owner_id`, the predecessor's `acquisition_result_uri`/`acquisition_result_sha256`, optional `topic`, and `AnalysisLimits` (`max_sources`, `max_bytes_per_source`, `max_text_chars`, `max_claims_per_source`, `near_duplicate_threshold`, `min_claim_chars`, `max_claim_chars` — clamped server-side in `services/analysis.py::_hard_limits`, never widened). In the worker path, the handler (`make_analysis_handler`) derives this directly from `context.input_artifacts`: it locates the artifact whose `artifact_type` equals `ACQUISITION_RESULT_ARTIFACT` — the same string as F3's real `defence_studio.acquisition.handler.ACQUISITION_MANIFEST_ARTIFACT_TYPE`, `"acquisition_manifest"` — among all completed-predecessor-stage artifacts the worker gathers (not only the immediate predecessor), and fails closed with `AnalysisInputError` if none is present.

**Input verification** — before any byte is read, `AnalysisService._load_acquisition` confirms the manifest artifact exists, re-computes its SHA-256 and compares it against the reference hash the worker claim carries (an independent integrity check, not a trust-on-read), and parses it as JSON. Any mismatch, missing file, or malformed JSON raises `AnalysisInputError` rather than fabricating a manifest. Per source, before normalizing: the chosen byte artifact's URI is resolved through the same path-containment guard as F1/F3 (`ArtifactStore._resolve`, rejecting traversal/absolute/backslash paths), its declared byte count is checked against `max_bytes_per_source`, its bytes are read with a hard size cap, and the actual SHA-256 of what was read is compared against the manifest's recorded hash — a mismatch is `ARTIFACT_CORRUPT`, not a lower-confidence pass-through.

**NormalizedSourceV1** (`defence-studio.normalized-source.v1`) — one per acquired source, `status` `NORMALIZED` or `FAILED`. Carries the detected language (a conservative Tamil-vs-Latin script heuristic, `ta`/`en`/`und` — not full language identification), the normalized text and its own SHA-256/char count, the verified `OriginalArtifactRef` (type/uri/sha256/bytes/media_type of the exact bytes normalized), an explicit `original_sha256_verified` flag, separated `SourceDates` (`published_at` only when F3 marked it `COLLECTED`, vs. `acquired_at`), and per-source warnings. Normalization (`defence_studio/analysis/normalize.py`) dispatches on media type: HTML (script/style stripped, block tags become paragraph breaks, entities decoded), WebVTT/SRT (cue text joined with preserved per-cue start/end timestamps and character offsets), and plain text/JSON (whitespace/Unicode NFC cleanup only). Unsupported media types or undecodable bytes raise `NormalizationError`, recorded as a `FAILED` source with an honest reason — never a fabricated transcript. Whitespace/boilerplate/markup is removed; qualifiers, negations, numbers, units, dates and designations are never touched by normalization.

**Deduplication** (`defence_studio/analysis/dedup.py`) — produces `DuplicateGroupV1` records with an explicit `basis`: `SAME_CANONICAL_URL` (the same URL acquired more than once), `IDENTICAL_CONTENT_HASH` (byte-identical normalized text from different URLs — syndication), or `NEAR_DUPLICATE_TEXT` (token-4-shingle Jaccard similarity at/above the configurable, tested `near_duplicate_threshold`, default `0.82`). Every original source record is preserved regardless of grouping; grouping never deletes or merges a source, and similarity is never treated as independence or as proof a claim is true. Independent sources merely discussing the same subject with different wording fall below the threshold and are deliberately left ungrouped.

**ExtractedClaimV1** (claim extraction in `defence_studio/analysis/claims.py`) — `claim_text` is always a verbatim sentence span from the normalized text (never paraphrased), with an `EvidencePassageV1` giving exact `start_offset`/`end_offset` (and, for subtitle sources, the covering cue's `timestamp_start`/`timestamp_end`). A candidate sentence is only extracted if it carries at least one detected factual signal (a quantity, date, designation, or named token) via conservative regex detectors; qualifiers (`reportedly`, `according to`, `estimated`, …) and negation are detected and recorded on the claim rather than removed, and `CandidateEntities` keeps designations/quantities/dates as deterministically matched substrings, not a typed NER classification F4 does not attempt. No AI model is invoked for this: `extraction_method` is always `"deterministic-sentence-span"` and `extractor_version` is a fixed constant, not a model name.

**Claim relationships** (`defence_studio/analysis/relationships.py`) — `ClaimGroupV1` groups claims with identical or near-duplicate text (entity-subject-blocked for cost, never all-pairs), always carrying the note that this is a textual relationship only, not corroboration. `ClaimConflictV1` flags same-subject claim pairs from *different* sources with opposite negation or mismatched quantities, always `flagged_for_review=True`; conflicting claims are never merged, resolved, or dropped — both sides remain in `AnalysisResultV1.claims`.

**AI-output validation seam** (`defence_studio/analysis/ai_schema.py`) — F4 calls no AI provider; this module exists only so a future AI-assisted extractor's output is forced through `validate_ai_payload`, which requires a list of objects each with a non-empty `claim_text`, in-range non-inverted integer `start_offset`/`end_offset`, a list-of-strings `qualifiers`, and a boolean `has_negation`. Any malformed item raises `AiOutputError` and the **whole** payload is rejected — one bad claim is never silently dropped while the rest are accepted as partial evidence.

**AnalysisResultV1** (`defence-studio.analysis-result.v1`) — the stage's output artifact (`artifact_type = "analysis_result"`, URI `jobs/<job_id>/research/analysis/<input_digest>.json`), carrying `normalized_sources`, `duplicate_groups`, `claims`, `claim_groups`, `conflicts`, `warnings`, `failures`, source/claim counts, `status` (`COMPLETED` or `COMPLETED_WITH_FAILURES`), and `AnalysisVersions` (normalizer/extractor/dedup version strings). `input_digest` is a SHA-256 over the acquisition hash, each normalized source's identity, and the processor versions/limits — it is both the artifact's filename and (via `run_and_store`'s check-before-write) the idempotency key: re-running over unchanged inputs reuses the existing artifact instead of rewriting it. (During F5's prerequisite review this guarantee was briefly observed broken by a wall-clock-timestamp bug, and a separate gap in `ARTIFACT_UNREADABLE` reporting was also observed; both were fixed before F5 was built — see "F4 implementation and verification" in `project_status.md` for the fix. F5 still pins every review decision to the job's current artifact SHA-256 at decision time rather than assuming any F4 output is permanently immutable across future reruns.)

**Durability** — the handler (`make_analysis_handler`) is retry-safe under the F2 contract (register it with `retry_safe_stages={ANALYSIS_STAGE}`) because its output is deterministic and content-addressed as above, writes are atomic through the existing `ArtifactStore`, and a failed/interrupted attempt commits nothing (fenced by F2) so the next attempt simply recomputes the same result. A missing or integrity-check-failing manifest raises `AnalysisInputError`, which the worker records as a durable stage failure under F2's existing retry/terminal policy; per-source problems (unsupported media type, corrupt/unreadable bytes, failed normalization) are recorded as `ProcessingFailure` entries and do not abort the other sources.

**Tests**: `tests/test_analysis_f4.py` — valid-artifact processing with full provenance/traceability, missing/malformed/unsupported/corrupted-artifact handling, exact and identical-content duplicate detection, near-duplicate grouping without merging independent sources, qualifier/negation/date/quantity/designation preservation, claim-to-passage offset traceability, cross-source conflict flagging without merging, malformed-AI-output rejection, repeat-processing idempotency, interrupted-processing retry through the real F2 `Worker` without a duplicate artifact version, cross-user rejection, and one end-to-end test that runs the real F3 `build_acquisition_handler` (via a mocked HTTP transport) feeding directly into the real F4 handler, both driven only by the F2 worker. All 21 pass as of F5's full-suite run.

## Phase 1A feed discovery contract

Purpose: turn an owner-approved research topic into ranked, provenance-preserving candidate sources for the owner to review and select from, without acquiring any content and without asserting that a candidate is true, trustworthy, or corroborated. Discovery runs only inside the F2 durable worker as the handler registered for the locked stage `news_feed_and_topic_discovery` (`defence_studio.contracts.discovery.DISCOVERY_STAGE`), the stage immediately before F3's `topic_search_and_source_collection`. Its predecessor, `application_foundation`, has no handler of its own; discovery's request artifact is attached there so it counts as an earlier-ordinal-stage artifact once the discovery stage claims.

**DiscoveryRequestV1** (`defence-studio.discovery-request.v1`, `defence_studio/contracts/discovery.py`) -- fields: `job_id`, `topic` (trimmed, 1-1000 chars, never reworded), `language` (2-20 chars, default `en`; `ta` supported), `search_terms` (up to 10 strings), `filters` (`DiscoveryFilters`: `source_types`, `providers` restricted to `SUPPORTED_PROVIDERS`, `date_from`/`date_to` ISO dates), and `limits` (`DiscoveryLimits`: `max_results`, `max_feeds_per_provider`, `timeout_seconds`, `max_redirects`, `max_bytes_per_fetch` -- clamped server-side in `discovery/service.py::clamp_limits`, never widened). `request_from_dict` rejects malformed/unsafe input (empty topic, non-positive limits, malformed dates, an inverted date range, an unknown provider) with a specific message rather than guessing a default.

**Seed URLs (`manual_url` provider)** -- optional `seed_urls` (list of <=20 http/https URLs, normalized and de-duplicated; default empty, so existing requests are unchanged). When present and `filters.providers` is empty, only `manual_url` runs; otherwise it never runs. Every fetch uses the SSRF-guarded fetcher with each redirect hop re-validated. Candidates carry `original_metadata.fetch_status=REACHABLE` and `reachability_only=true` (HTTP 200 proves reachability, not accuracy); a publication date is recorded only if the page declares one. Unreachable, non-HTML, <200-character and identical-content URLs are reported in the provider outcome and produce no candidate.

**Submitting a request (pre-queue, synchronous HTTP)** -- `POST /api/jobs/{job_id}/discovery/requests` validates the body and writes it as a `discovery_request` artifact against `application_foundation` via `JobService.add_pretransition_artifact` (a new, narrowly-scoped method: it allows an artifact on a stage that has not started yet, but only while the job is still `DRAFT`, so there is no worker-claim race to protect against). Submitting again before the job is queued is idempotent by content hash (identical payload reuses the existing artifact version instead of writing a duplicate); submitting after the discovery stage has started is rejected with `409 Conflict`. The owner must still call the existing `POST /api/jobs/{job_id}/queue` endpoint themselves -- discovery does not auto-queue.

**DiscoveryResultV1** (`defence-studio.discovery-result.v1`) -- the stage's output artifact (`artifact_type = "discovery_result"`, URI `jobs/<job_id>/research/discovery_result.json`), carrying `candidates` (one `DiscoveryCandidateV1` per deduplicated canonical URL), `providers` (one `ProviderOutcome` per provider that ran: `OK`/`PARTIAL`/`COMPLETED_NO_RESULTS`/`UNAVAILABLE_MISSING_CREDENTIALS`/`UNAVAILABLE_NOT_CONFIGURED`/`ERROR`, with an honest `message` and `requires_credentials`/`optional_dependency` flags), `dedup_notes`, `warnings`, `requested_limit`/`returned`, and `status` (`COMPLETED`/`COMPLETED_WITH_FAILURES`/`COMPLETED_NO_RESULTS`). One provider's failure never blocks the others.

**DiscoveryCandidateV1** -- `candidate_id` (stable SHA-256-derived key over the canonical URL, reusing F3's own `normalize_url`), `declared_metadata` (title/publisher/published_at/language, each paired with the same `MetadataStatus` tri-state F3 uses -- a value F3 would recognize as `COLLECTED`/`UNAVAILABLE`/`NOT_COLLECTED`), `ranking` (`RankingFactors`: `relevance_score`, `recency_score`, `language_match_score`, `source_type_score`, `total_score`, and an `explanation` tuple of human-readable reasons -- `defence_studio/discovery/ranking.py` computes these deterministically from metadata the provider actually returned; a missing publication date yields a neutral 0.5 recency score and an explicit "no publication date" explanation line, never a fabricated one), `provider`/`provider_version`, and `merged_from_providers` (other providers that returned the exact same canonical URL -- the *only* basis for merging; two different publishers with merely similar titles are always kept as separate candidates).

**Providers** (`defence_studio/discovery/providers.py`) -- `rss_feed` (a *working* provider requiring no credentials: reads feed URLs from `DEFENCE_STUDIO_DISCOVERY_RSS_FEEDS`, one set per language, parses RSS 2.0/Atom with the stdlib `xml.etree.ElementTree`, and keyword-matches entries against the topic/search terms; reports `UNAVAILABLE_NOT_CONFIGURED` rather than silently returning nothing when no feed is configured for the requested language) and `configured_search_api` (*requires credentials*: `DEFENCE_STUDIO_DISCOVERY_SEARCH_API_KEY` + `DEFENCE_STUDIO_DISCOVERY_SEARCH_API_URL`; reports `UNAVAILABLE_MISSING_CREDENTIALS` and makes no network call when either is unset; otherwise performs one guarded GET expecting `{"results": [{"title","url","snippet","published_at"}, ...]}`). Both go through F3's existing `GuardedFetcher`/`UrlGuard` (`defence_studio.acquisition.http_client`/`url_guard`) -- no new fetch path, no new SSRF surface. No paid/optional dependency is required for the `rss_feed` provider to work; `configured_search_api` is disabled by default until a deployment supplies its own credentials and endpoint.

**Browsing, filtering, and selecting (post-run, synchronous HTTP)** -- `GET /api/jobs/{job_id}/discovery/candidates[?language=&source_type=&provider=&min_score=&query=]` is a read-model over the latest `discovery_result` artifact (empty-state when none exists yet); `GET .../discovery/candidates/{candidate_id}` returns one. `POST /api/jobs/{job_id}/discovery/selection` validates the submitted `candidate_ids` (non-empty, <=50, no duplicates, all known to the current result, and the discovery stage must be `COMPLETED`) and writes an **F3-compatible `acquisition_request` artifact** (`defence_studio.contracts.acquisition.request_from_dict` parses it unmodified -- verified in `tests/test_discovery_f1a.py::test_select_candidates_produces_f3_compatible_acquisition_request`) against the (now completed) discovery stage, so F3's worker handler picks it up exactly like any other earlier-stage artifact. Re-submitting an identical selection reuses the existing artifact version instead of creating a duplicate (content-hash idempotency, the same pattern F4 uses for its own output). `GET .../discovery/selection` returns the currently confirmed candidate IDs so the UI can resume after a refresh. Discovery never calls F3 directly and never marks a candidate acquired, verified, or approved -- selection only produces F3's own input artifact; F3 still runs through its own worker claim.

**Tests**: `tests/test_discovery_f1a.py` -- request validation (empty topic, invalid limit, malformed/reversed date range, unknown provider, topic never reworded), provider behavior (`UNAVAILABLE_NOT_CONFIGURED`/`UNAVAILABLE_MISSING_CREDENTIALS` with no network call, topic keyword matching, partial success across multiple feeds), deterministic ranking and neutral-not-fabricated missing-date scoring, canonical-URL dedup across providers versus distinct publishers with similar titles staying separate, SSRF-guard reuse (a feed resolving to a private address is blocked), full run through the real F2 `Worker` (missing-request fail-closed case, successful run, and a simulated lease-expiry retry), and the API-facing service (request idempotency, cross-owner denial via `DiscoveryNotFound`, conflict once discovery has started, selection validation, the discovery-to-F3 contract handoff, and cross-owner candidate-listing denial through `TestClient`). 26 new tests; full backend suite 134 passed, 2 skipped (F3's pre-existing opt-in live-provider checks, unchanged).

## F5 evidence review contract

Purpose: record explicit, authenticated, auditable human decisions over F3/F4 output. F5 is an evidence-review boundary, not automatic fact-verification — it never mutates an acquisition/analysis artifact and never asserts a claim is true. Unlike F3/F4, F5 has synchronous HTTP endpoints, because review is a human-paced action rather than a durable background stage.

**ReviewDecisionRequestV1 / ReviewDecisionRecordV1 / ReviewHistoryEntryV1** (`defence-studio.review-decision.v1` / `defence-studio.review-history.v1`, `defence_studio/contracts/review.py`) — a decision is `APPROVED_FOR_USE`, `REJECTED`, `NEEDS_MORE_EVIDENCE`, or `CONFLICT_UNRESOLVED` against either a `CLAIM` or a `SOURCE`, pinned to `reviewed_artifact_sha256` (the exact `analysis_result`/`acquisition_manifest` bytes the reviewer saw) and `expected_revision` (optimistic concurrency). All four decisions are reachable from any other decision or from no prior decision — the enforced constraint is revision-exactness and concurrency, not a restrictive state graph (see the module docstring for the rationale, including what `APPROVED_FOR_USE` does and does not authorize).

**Persistence** (SQLite schema v3, `database.py::_upgrade_v2_to_v3`) — additive-only `claim_reviews`/`source_reviews` (current decision, one row per `(job_id, claim_id|source_id)` `PRIMARY KEY`) and `claim_review_history`/`source_review_history` (append-only; `UNIQUE(job_id, subject_id, reviewer_id, idempotency_key)` makes a duplicate submission idempotent rather than a second audit row). No F1–F4 table, column, or row is touched; a decision references `job_id` (FK to `workflow_jobs`) and an opaque `claim_id`/`source_id` string validated against the *current* artifact's content at decision time — not a duplicate identity system.

**Service rules** (`services/review.py::ReviewService`) — every call verifies job ownership first (404-equivalent on mismatch, same as every other boundary). `decide_claim`/`decide_source` run inside one `BEGIN IMMEDIATE` transaction: replay of the same `(subject, reviewer, Idempotency-Key)` returns the existing record unchanged; `reviewed_artifact_sha256` not equal to the job's current artifact → `StaleRevision` (409); `expected_revision` not equal to the current stored revision → `RevisionConflict` (409, prevents a concurrent decision from being silently overwritten); unknown decision value or unknown `claim_id`/`source_id` against the current artifact → `ReviewValidationError` (422). `list_claims`/`list_sources` are read-models that merge the latest `analysis_result`/`acquisition_manifest` artifact with current review state, exposing `has_conflict`, `duplicate_groups`, and `is_stale` (a stored decision's SHA-256 no longer matching the current artifact) without ever resolving a conflict or merging a duplicate automatically.

**HTTP endpoints** — `GET /api/jobs/{job_id}/review/sources[?status=]`, `GET .../sources/{source_id}`, `GET .../sources/{source_id}/history`, `POST .../sources/{source_id}/decisions` (requires `Idempotency-Key`); claim equivalents under `.../review/claims[?status=&conflict=&source_id=]`. All require the same HS256 bearer token as every other endpoint. `create_app()` gained an optional `storage_root_path` parameter (defaults to `config.storage_root()`) so tests/deployments can point the review service's artifact reads at an isolated directory, mirroring the existing `database_file` override.

**Frontend** — `frontend/` is a new, framework-free static app (plain HTML/CSS/ES modules, no build step) served by FastAPI via `StaticFiles` mounted at `/` (registered after all `/api/...` routes so it never shadows them). This is the first UI Defence Studio has; see `component_registry/REGISTRY.md` for the primitives it introduces (status badge, confirm dialog, text field) and `project_status.md` for the manual mobile-Chrome verification still outstanding.

**Tests**: `tests/test_review_f5.py` — decision creation/retrieval, invalid decision/unknown-subject rejection, cross-owner denial, stale-revision rejection, optimistic-concurrency conflict, idempotent replay, append-only history ordering, conflicting-claim/duplicate-source surfacing and filtering, schema v2→v3 migration against a reconstructed real legacy database (preserving an existing job row), unsupported-version fail-closed, persistence across a fresh service instance (simulated restart), and API-level auth/stale/conflict/validation status codes via `TestClient`.

## Phase 2 evidence-package, timeline, approval & export contract

Purpose: assemble the research job's acquired sources, extracted claims/passages, duplicates, conflicts, review decisions, and a provenance-preserving timeline into a single evidence package; gate an explicit human approval against the exact package revision; and export a canonical, deterministic JSON package. Phase 2 is the research-package/approval boundary — it never generates a script, audio, scenes, video, or published content (that is Phase 3+). It mutates no F3/F4 artifact and never asserts a claim is true.

**Single engine, canonical routes.** `defence_studio.services.evidence.EvidenceService` (subclass of `ReviewService`, reusing its ownership/artifact-read/integrity helpers) is the only package engine. The HTTP surface is the core-design-named `/package/*` + `/timeline` set; an earlier parallel `/evidence/*` route tree built in a concurrent session was retired during reconciliation so there is exactly one implementation and no duplicate routes.

- `GET /api/jobs/{job_id}/timeline[?start=&end=&source_id=&claim_id=&language=]` — ordered timeline events. Four distinct time kinds are kept distinct and never merged: `PUBLICATION` (source published), `ACQUISITION` (source acquired), `ANALYSIS` (analysis run), `REVIEW` (review decision), plus `CLAIM_PUBLICATION` where a claim carries its own source-published date. Each event's date is normalized via `contracts/evidence.py::timestamp`, which preserves the original value and classifies precision as `TIMESTAMP` / `DATE_ONLY` / `TIMEZONE_UNKNOWN` / `UNRELIABLE` / `MISSING` — a missing or unparseable date is **never fabricated**. Time-range filters require ISO timestamps with a timezone and explicitly exclude undated/timezone-unknown events (disclosed in the response `note`).
- `GET /api/jobs/{job_id}/package` — the assembled DRAFT package plus its content `revision` (sha256 of the canonical body), the approval ledger, and the current-revision approval (if any). Always inspectable; a DRAFT is never eligible for downstream use (`status="DRAFT"`, `approval=null`).
- `GET /api/jobs/{job_id}/package/readiness` — `ready`, machine-readable `blockers`, `limitations`, `eligible_claim_ids`, and the current approval. `ready` is exactly `not blockers` (enforced by `validate_package`).
- `POST /api/jobs/{job_id}/package/approve` (requires `Idempotency-Key`; body `{revision, note}`) — explicit human approval. See the gate below.
- `GET /api/jobs/{job_id}/package/export[?draft=false]` — canonical JSON; `draft=true` returns the current snapshot, otherwise the stored approved package (409 if the current revision is unapproved). Served with `Content-Disposition: attachment` and `Cache-Control: no-store`.

**EvidencePackageV1** (`defence-studio.evidence-package.v1`, policy `defence-studio.evidence-approval.strict.v1`, `contracts/evidence.py`) is a strict (`extra="forbid"`) model carrying: artifact references (type/uri/sha256/schema), discovery selection + selected candidates, per-source views (with normalized metadata and current review), per-claim views (with passage + current review), duplicate groups, claim groups, conflicts, audit history, timeline, `limitations`, `blockers`, `eligible_claim_ids`, `ready`, `status`, and `approval`. `validate_package` rejects a forged `ready`/`status`/`approval` combination.

**Readiness / approval gate** (`EvidenceService._assemble`) is conservative and explicit. A package is blocked unless, for the current revision: both `acquisition_manifest` and `analysis_result` exist and the analysis references the current acquisition revision; the acquisition and analysis stages are `COMPLETED`; every source has a current (non-stale) final decision (`APPROVED_FOR_USE`/`REJECTED`) with a non-blank note; every claim likewise, and an `APPROVED_FOR_USE` claim's supporting source is itself currently approved; each source byte artifact re-hashes to its recorded sha256 (else a "missing or corrupt" blocker); each claim's passage offsets are valid and `text[start:end]` exactly equals both the passage text and the verbatim claim text, referencing the normalized source's original artifact URI; normalized-text checksums match; analysis source coverage matches acquisition; selected-target coverage matches; and every flagged conflict has at least one side explicitly `REJECTED` (rejecting one side never erases it — rejected evidence stays visible in the package and audit trail). Missing publication dates/publishers and incomplete acquisition/normalization are surfaced as `limitations`, not silently dropped.

**Approval & audit** (schema v4, `database.py::_upgrade_v3_to_v4`, additive) — an append-only `evidence_packages` ledger (`PRIMARY KEY(job_id, version)`, `UNIQUE(job_id, revision)`, `UNIQUE(job_id, idempotency_key)`). `approve` runs in `BEGIN IMMEDIATE`: requires a non-blank note; replays an identical `(job_id, Idempotency-Key)` (409 if the key was used for a different revision/note); recomputes the package and rejects if `revision != digest(body)` (evidence/review changed) or if `blockers` remain (`StaleRevision`, 409); writes the canonical approved bytes to a content-addressed artifact and one ledger row. Approval is bound to the exact content revision, so any later change makes the old approval stale for the changed package. Generic artifact registration, job completion, package generation, and export never confer approval. `export` re-validates the stored package against the current revision/ledger and refuses a stale or unapproved revision.

**Deterministic export** — the canonical body excludes nothing material and is byte-identical for identical inputs + review state (generation timestamp and approval envelope live outside the hashed revision); repeated export of unchanged content is idempotent.

**Research worker** (`defence_studio/research_worker.py`, `python -m defence_studio.research_worker`) — an opt-in production entry point that registers only the four authorized Phase-1 handlers (foundation, discovery, acquisition, analysis) on the **existing** F2 `Worker` (no second worker architecture) and stops at the human-review boundary; no script/voice/render/publish handler is registered.

**Phase 3** — now implemented as a full generation/review/approval surface; see the "Phase 3 source-grounded script generation" section below. `services/script_contract.py::prepare_request` is retained as a thin offline request-shaping helper over the same approved+exported package, but Phase 3's live path is `services/script.py::ScriptService` + the `/api/jobs/{job_id}/script/*` routes.

**Tests**: `tests/test_evidence_package.py` (21) — timestamp precision classification, readiness blockers (missing artifacts, stale reviews, blank notes, invalid passage offsets, corrupt bytes, unresolved conflicts, coverage mismatch), revision-bound idempotent approval and replay-mismatch rejection, stale-after-change and unapproved-export refusal, cross-owner denial, deterministic export, schema v3→v4 migration incl. fail-closed on a missing singleton, forged-flag rejection, and the Phase 3 offline boundary. `tests/test_research_pipeline.py` (3) — the full offline pipeline through the real worker (discovery → human-selection gate → acquisition → analysis → human-review gate → draft readiness → approve → export), selection-revision immutability + lock-after-claim, and discovery-request update preserving prior bytes. API-level auth/status codes are covered in `test_evidence_package.py` and re-confirmed by a live HTTP smoke test on the `/package/*` + `/timeline` routes.


## Phase 3 source-grounded script generation, validation, review & approval

Purpose: turn an **approved** Phase 2 evidence package into a human-reviewable, source-grounded narration script — in Tamil and/or English — then require an explicit human approval of a specific revision and expose that approved revision as a stable input contract for Phase 4. Phase 3 never does TTS, voice, scene/image/video, rendering, or publishing (that is Phase 4+). It mutates no F3/F4/Phase-2 artifact and never asserts a claim is true; structural/evidence validation establishes *groundedness in approved evidence*, not truth.

**Single engine.** `defence_studio.services.script.ScriptService` subclasses `EvidenceService` (reusing ownership checks, the artifact store, and package assembly). Human-paced like F5/Phase 2 (synchronous HTTP, not a worker stage). The provider is only ever invoked from `generate()` on an explicit authorized POST — never during a read, package inspection, job creation, or review.

**Routes** (all require a verified bearer token; owner-scoped; `language in {ta, en}`):
- `GET /api/jobs/{job_id}/script/revisions[?language=]` — list revision rows (version, language, status, hashes, timestamps).
- `GET /api/jobs/{job_id}/script/revisions/{language}/{version}` — the full stored revision artifact (narration + evidence mapping + validation + usage). The lifecycle `status` is overlaid from the authoritative DB row.
- `GET /api/jobs/{job_id}/script/revisions/{language}/{version}/history` — append-only review-action history.
- `POST /api/jobs/{job_id}/script/generate` (requires `Idempotency-Key`; body `GenerationConfigV1`) — explicit generation; `201` with the new revision.
- `POST /api/jobs/{job_id}/script/revisions/{language}/{version}/request-changes` (requires `Idempotency-Key`; body `{note}`).
- `POST /api/jobs/{job_id}/script/revisions/{language}/{version}/approve` (requires `Idempotency-Key`; body `{revision_sha256, note}`).
- `GET /api/jobs/{job_id}/script/export/{language}` — the APPROVED revision for Phase 4; `409` if none / superseded / evidence no longer current. `Content-Disposition: attachment`, `Cache-Control: no-store`.

**GenerationConfigV1** (`contracts/script.py`, strict) — `language`, `audience`, `tone`, `script_format`, `target_duration_seconds` (30-3600), `target_words` (100-5000), `model`, `prompt_version` (`defence-studio.source-grounded-script.v1`), `max_text_cost_inr` (>0, <=1000), `terminology` (English-term preservation map). No secret ever appears in config.

**ScriptRevisionV1** (`defence-studio.script-revision.v1`, strict) — the immutable persisted artifact: `job_id`, `language`, `script_type`, `version`, `package_sha256` (binds to the exact approved package), `request_sha256`, `title`, optional `opening_hook`, ordered `sections` (each `NarrationSectionV1`: spoken `narration` only, with a **separate** machine-readable `evidence` map — `claim_ids`/`source_ids`/`qualification` — kept out of narration so citation IDs are never spoken, plus an optional `presentation_note`), `closing`, `config`, `usage` (`UsageV1`), `word_count` (`WordCountV1`), `validation` (`ValidationResultV1`), `status`, `created_at`, `eligible_claim_ids` (snapshot at generation), and `approval` (`ScriptApprovalV1` or null). A model validator enforces: `approval` iff `status=="APPROVED"`; not APPROVED while validation failed; config language matches; validation bound to the revision's package hash.

**Status lifecycle** — `VALIDATION_FAILED` -> (fix via a new revision), `AWAITING_REVIEW`, `CHANGES_REQUESTED`, `APPROVED`, `SUPERSEDED`. Approval is never implied by generation, validation success, or export. Approving a revision supersedes any previously-approved revision of the **same language**, keeping exactly one APPROVED revision per language; approving Tamil never affects English and vice-versa (independent `(job_id, language, version)` lineages).

**Generation fail-closed conditions** (`generate`, revalidated immediately before the provider call): the current evidence snapshot must be `ready` and match a row in the `evidence_packages` approval ledger whose stored artifact is genuinely `APPROVED` (so a missing/stale/unapproved package, a later review change, or corrupted evidence bytes all block generation before any provider spend); job ownership; bounded config. A duplicate `(job_id, language, Idempotency-Key)` replays the existing revision — a retry never creates a second revision and never double-spends. Provider failures (`timeout`/`rate_limited`/`provider_error`/`malformed_response`/`missing_api_key`) raise `ScriptGenerationFailed` (HTTP 502) and write nothing, so the idempotency key stays unconsumed and a retry is safe. A measured cost over `max_text_cost_inr` fails closed.

**Evidence-grounded validation** (`services/script_validation.py`, `defence-studio.script-validator.v1`, deterministic, pure) — every section that asserts material facts (either flagged `requires_evidence` or heuristically detected via numbers/quotes) must cite >=1 `claim_id`; referenced claims must exist in the approved package and be in its `eligible_claim_ids`; a claim's supporting source must be in the package; a citation ID must never appear inside spoken narration (`CITATION_LEAKED_INTO_NARRATION`); title and closing are required. ERROR-severity issues set `passed=false` (-> `VALIDATION_FAILED`, un-approvable); missing qualification is a WARNING. The validator never asks the model to judge its own output.

**Word count / duration** (`contracts/script.py`) — `count_words` is a deterministic whitespace split over spoken text only (hook + each section narration + closing; headings/notes/evidence excluded so they are never counted or spoken). `estimate_duration` (`words-per-minute.v1`, default 150 wpm) yields an explicit **estimate** (`is_estimate: true`), never presented as an exact recording time.

**Provider & cost** (`providers/openai_text.py`) — `OpenAiTextProvider` is a bounded, retrying Chat-Completions client behind a `client_factory` seam (tests inject `httpx.MockTransport`; **no API credits spent in the suite**, no `openai` SDK dependency). API key from `DEFENCE_STUDIO_OPENAI_API_KEY` (never logged; prompt contents not logged). Retries 429/5xx up to a bound; distinguishes retryable vs non-retryable. `UsageV1` records provider/model, token counts (or `tokens_available=false`), retries, `measured_text_cost_inr` + `cost_is_measured` (measured vs unavailable kept explicit — never fabricated), `pricing_source` (`defence-studio.openai-pricing.manual.v1`, stored so a cost is reproducible) and `currency`. Cost is computed from a stored INR pricing table times a configurable USD->INR rate; the Rs.10/video target is measured, not asserted. A live smoke test is opt-in only.

**Approval & audit** (schema v5, `database.py::_upgrade_v4_to_v5`, additive) — immutable `script_revisions` (`PRIMARY KEY(job_id, language, version)`, `UNIQUE(job_id, language, revision_sha256)`, `UNIQUE(job_id, language, idempotency_key)`) + append-only `script_review_history`. `approve`/`request_changes` run in `BEGIN IMMEDIATE`, verify ownership, replay a duplicate `(..., reviewer, Idempotency-Key)`, reject a wrong `revision_sha256` (`StaleRevision`/409), refuse approval of a validation-failed/already-approved/superseded revision, and re-check that the revision's `package_sha256` still matches the current ready+ledgered approved evidence (a later evidence change blocks approval, not just generation). Approval writes a rewritten APPROVED artifact + one history row, binding to the exact revision hash. `export` re-checks approval + package currency and refuses otherwise.

**Phase 4 boundary** — `services/script.py` imports nothing related to TTS/voice/rendering/ffmpeg/youtube/publish (asserted by a test parsing its import graph). The deliverable is an approved, versioned, source-grounded script artifact with provenance, evidence mapping, validation results, language identity, and cost metadata, consumable without modifying the Phase 3 module.

**Tests**: `tests/test_script_phase3.py` (28) — generation blocked without/with-stale evidence approval and for corrupted evidence bytes; cross-owner denial; Tamil/English independence + per-language approval isolation; terminology passed into the prompt; missing/unknown/unapproved claim references and citation-leak failing validation; deterministic word-count/duration + pure revalidation; provider timeout/rate-limit/malformed/missing-key behavior and retry (via `httpx.MockTransport`); idempotent duplicate generation; immutable versioned revisions; approval bound to the correct hash; changes-requested -> new revision -> fresh approval; supersession; approval invalidated by changed evidence; reviewer-note required + history; measured-vs-unavailable cost and over-budget fail-closed; API auth/error codes via `TestClient`; approved-export + Phase-4 import boundary. Live HTTP smoke on the real server (port 8022, temp DB) confirmed: static `script-view.js` serves, unauthenticated->401, job-create->201, empty revisions->200, export-before-approval->409, cross-owner->404, generate-without-approved-package->409 (fail-closed).

## Phase 4 scene-plan contract (M0 — contract foundation only)

Purpose: define the **stable, versioned** scene-plan shape that future Phase 4–7 components (scene service, TTS adapter, alignment adapter, render adapter) will implement independently, so they can be built against a fixed schema without coupling to one another. **M0 is a contract only**: `contracts/scene.py` runs no network call, touches no database, imports nothing from TTS/alignment/FFmpeg, defines no route, and generates no scenes. Scene generation, editing, approval persistence, and any downstream integration are later milestones (M1+), explicitly not in M0.

**Two boundaries** (mirroring `contracts/script.py`, reusing its `StrictModel`/`digest` from `contracts/evidence.py` — no parallel contract style):
- **Request** — `ScenePlanRequestV1` (`defence-studio.scene-plan-request.v1`, strict): the instruction to build a plan, pinned to its upstream approvals — `job_id`, `language` (`ta`/`en`), `script_revision_sha256` + `script_version` (the exact approved Phase 3 revision it derives from), `package_sha256` (that revision's approved evidence package), and a bounded `ScenePlanConfigV1` (`language`, `target_total_seconds` 30–3600, `words_per_minute`, `default_transition`). A model validator requires the config language to match the request language. It carries no narration and no scenes.
- **Persisted artifact** — `ScenePlanV1` (`defence-studio.scene-plan.v1`, strict): the versioned, editable, re-orderable plan — `schema_version`, `job_id`, `language`, `version`, `planner_version` (`defence-studio.scene-plan.v1`), the upstream binding (`script_revision_sha256`/`script_version`/`package_sha256`), ordered `scenes` (1–500), `eligible_claim_ids` (snapshot of the approved package's approvable claims, retained so scene claim references validate reproducibly), `status`, and `created_at`.

**SceneV1** — one ordered scene: `scene_id`, `order` (1-based, must equal position), `source_section_id` (the approved script section the narration was sliced from), verbatim spoken `narration` (never rewritten here), `claim_ids` (approved-evidence claims the slice rests on; may be empty for a non-material scene), `purpose`, and presentation/delivery metadata kept strictly **out** of spoken text — `voice_direction` (`VoiceDirectionV1`: tone + bounded relative `rate`/`pitch` around 1.0 + `pause_after_ms`; metadata only, never voiced), `visual_suggestions` (non-binding ideas, **not** asset assignments — assets/rights are Phase 5, a separate contract; nothing fabricates a URL or rights basis), `captions` (`CaptionCueV1`), `transition_in`, optional `crop` (`CropHintV1`: provider-independent aspect ratio + normalized focus point), optional `music` (`MusicCueV1`: intent + bounded gain, no audio file). Plus the timing + downstream slots below.

**Planned vs measured timing (honesty rule).** `planned_timing` (`PlannedTimingV1`) is always present and **always an estimate** (`is_estimate` pinned `True`), derived deterministically from the scene's spoken word count at a words-per-minute rate (`words-per-minute.v1`, the same method the script contract uses; `plan_scene_timing`/`count_words` helpers). `measured_timing` (`MeasuredTimingV1`) is `None` until real alignment has run — it carries `start_seconds`/`duration_seconds`, the producing `alignment_sha256`, and `is_synthetic` (propagated unchanged from the alignment engine's own flag so a render can never present deterministic/test timing as genuine alignment). The contract **rejects a measured timing with no referenced alignment artifact** (plan-level: `measured_timing` requires the scene's `alignment_ref`) and a `measured_timing.alignment_sha256` that disagrees with `alignment_ref.sha256`. No measured word/scene timing can exist before alignment.

**Downstream references are slots, not internals.** `audio_ref`/`alignment_ref`/`render_ref` (each an `ArtifactRefV1`: `artifact_type` + `uri` + `sha256` + the producing artifact's own `schema_version` — nothing else) are optional per-scene pointers to artifacts produced by other components, default `None` in M0, populated by later milestones. They let a plan bind to and re-verify TTS/alignment/render outputs by hash (the "never trust, re-verify" pattern F4 already applies) without embedding any component's internal payload.

**Status lifecycle** — `DRAFT` → `AWAITING_REVIEW` → `CHANGES_REQUESTED` → `APPROVED` → `SUPERSEDED`. Defined now so M1's generate/edit/approve has a fixed target; approval binding to a plan hash (and to the script revision it was built from, the same stale-revision 409 pattern as Phase 2/3) is implemented in M1, **not** M0.

**Validation** (`validate_scene_plan` / `validate_request`, deterministic, pure): `extra="forbid"` rejects any unknown field (plan or scene level); scene `claim_ids` must be a subset of `eligible_claim_ids` (a scene can never cite a claim absent from the approved evidence); `scene_id`s must be unique and `order` must match position (out-of-order/duplicate rejected); narration must contain non-whitespace spoken text; per-scene `claim_ids` carry no duplicates; all hashes are 64-hex; `schema_version`/`planner_version` are pinned literals. `plan_digest` is the canonical-JSON content hash (same as evidence/script artifacts) — identity-stable and input-key-order-independent — for a future service to bind approval to.

**Phase 4 boundary** — `contracts/scene.py` imports only `contracts/evidence.py` (`StrictModel`/`digest`); nothing from TTS/alignment/FFmpeg/render, no route, no DB, no provider. The deliverable is a fixed scene-plan schema derivable from an approved Phase 3 export and extensible with the already-reserved timing/reference slots, consumable by later milestones without changing this module.

**Tests**: `tests/test_scene_contract_m0.py` (15, contract-only — no network, no DB) — a scene plan derived from a realistically-shaped **approved** `ScriptRevisionV1` export validates; request validation + config/language-mismatch rejection; serialization round-trip + deterministic/input-order-independent `plan_digest`; the three M0-named rejection cases (unknown field, a scene citing a claim absent from the approved package, out-of-order/duplicate `scene_id`); required-field and invalid-value rejection (bad hash, unknown status/planner/language, empty narration, duplicate scene claims, out-of-range voice/crop); the planned-vs-measured timing honesty rule (planned is always an estimate; measured requires + must hash-match a referenced alignment artifact; `is_synthetic` carried through); downstream reference slots absent by default and carrying no internals; and contract-version identification (pinned `schema_version`/`planner_version` literals).

## Phase 4 scene planning, persistence, editing & approval (M1)

Purpose: turn an **approved** Phase 3 script revision into an editable, versioned scene plan, persist it, support per-scene add/remove/reorder/edit without rebuilding untouched scenes, and require an explicit human approval of a specific plan version. Human-paced like F5/Phase 2/Phase 3 (synchronous HTTP under `/api/jobs/{job_id}/scene/*`, **not** a worker stage). **M1 does no TTS/alignment/render/asset/rights work** — a scene's downstream reference slots stay empty; `generate` is deterministic and **never calls any text/TTS/alignment/render provider**.

**Single engine, reused.** `defence_studio.services.scene.SceneService` subclasses `ScriptService` (→ `EvidenceService` → `ReviewService`) purely to reuse job-ownership checks, the `ArtifactStore`, the note/idempotency-key validators, and `export_approved()` (the Phase 3→4 boundary returning the one currently-approved, still-fresh script revision). No second execution architecture; no provider is invoked on any path.

**Routes** (all require a verified bearer token; owner-scoped; `language in {ta, en}`; `SceneService` raises the `ReviewError` family so the existing handler maps every status code):
- `GET /api/jobs/{job_id}/scene/plans[?language=]` — list plan rows (version, language, status, hashes, upstream bindings, timestamps).
- `GET /api/jobs/{job_id}/scene/plans/{language}/{version}` — the full stored plan body (`ScenePlanV1`), with the authoritative DB `status` overlaid.
- `GET /api/jobs/{job_id}/scene/plans/{language}/{version}/history` — append-only review-action history.
- `GET /api/jobs/{job_id}/scene/plans/{language}/{version}/scene-digests` — map of `scene_id` → canonical per-scene content hash (makes the per-scene isolation property observable).
- `POST /api/jobs/{job_id}/scene/generate` (requires `Idempotency-Key`; body `ScenePlanConfigV1`) — deterministic initial plan from the approved script export; `201`.
- `POST /api/jobs/{job_id}/scene/plans/{language}/revise` (requires `Idempotency-Key`; body `{base_version, edits}`) — a new DRAFT version applying only the requested scene edits; `201`.
- `POST /api/jobs/{job_id}/scene/plans/{language}/{version}/request-changes` (requires `Idempotency-Key`; body `{note}`).
- `POST /api/jobs/{job_id}/scene/plans/{language}/{version}/approve` (requires `Idempotency-Key`; body `{plan_sha256, note}`).

**Deterministic initial plan.** `generate` reads `export_approved(job, owner, language)` (fails closed — `ScriptStaleRevision`/409 — if there is no approved revision or its evidence is no longer current), then builds exactly one scene per approved-script section, in order, plus the opening hook and closing as their own scenes when present. Narration is copied **verbatim**; each section's approved `claim_ids` (intersected with the package's eligible set) ride along; a per-scene words-per-minute **planned-timing estimate** is attached; no narration is rewritten, no claim invented, no timing measured. The plan is bound to the exact approved-script `revision_sha256` and its `package_sha256`.

**Editing (`revise`), isolation + conflict protection.** Supported `edits` keys: `reorder` (a permutation of the current `scene_id`s), `remove` (list of `scene_id`s), `update` (`{scene_id: {field: value}}`, only the editable presentation/narration fields — `narration`, `claim_ids`, `purpose`, `voice_direction`, `visual_suggestions`, `captions`, `transition_in`, `crop`, `music`; never `order`, which is always recomputed), and `add` (`{at?, scenes:[…]}`). An unknown op, an unknown/duplicate `scene_id`, a non-editable field, a non-permutation reorder, a claim outside the approved eligible set, or removing every scene all raise `SceneValidationError`/422. **Per-scene isolation**: an untouched scene's dict is carried through unchanged and canonical JSON is deterministic, so its stored content hash is identical across the new version (the M1 acceptance property, exercised via `scene-digests`). **Revision conflict**: only the latest version may be edited; editing a stale `base_version` raises `SceneRevisionConflict`/409 rather than silently overwriting.

**Persistence (schema v6, `database.py::_upgrade_v5_to_v6`, additive).** Immutable, content-addressed `scene_plans` (`PRIMARY KEY(job_id, language, version)`, `UNIQUE(job_id, language, plan_sha256)`, `UNIQUE(job_id, language, idempotency_key)`) + append-only `scene_plan_review_history`. `(job_id, language, version)` is the plan identity; Tamil and English are independent lineages (approving one never approves the other), exactly like `script_revisions`. Each row records the `script_revision_sha256`/`script_version` and `package_sha256` the plan was built from. No F1–F5/evidence/script table is touched; DDL + version bump commit together inside `BEGIN EXCLUSIVE` and roll back together on failure; accepted prior versions are `{1,2,3,4,5,6}`.

**Identity & digest.** A plan is content-addressed: its canonical-JSON digest (`contracts/scene.py::plan_digest`, same `canonical`/`digest` as evidence/script artifacts) is its `plan_sha256`. `generate`/`revise` return the content-addressed plan **body** (like `ScriptService.generate`); the `plan_sha256` is the row value and equals `digest(body)`. Byte-identical plans collide by design; a duplicate `(job_id, language, Idempotency-Key)` replays the existing version rather than creating a second.

**Approval & re-sync gate.** `approve` runs in `BEGIN IMMEDIATE`, verifies ownership, replays a duplicate `(…, reviewer, Idempotency-Key)`, rejects a wrong `plan_sha256` (`SceneStaleRevision`/409), refuses an already-APPROVED/SUPERSEDED plan, and — the M1 re-sync rule — **re-checks that the plan's `script_revision_sha256` is still the current approved script export**; if the approved script changed/was re-approved (or is no longer current), approval is refused (`SceneStaleRevision`/409) until the plan is regenerated/re-synced against the new script. Approval supersedes the previously-approved plan of the **same language** only, keeping exactly one APPROVED plan per language. Approval is never implied by generation or editing. `request_changes` moves a DRAFT/CHANGES_REQUESTED/AWAITING_REVIEW plan to `CHANGES_REQUESTED` with a required note + history row; a terminal (APPROVED/SUPERSEDED) plan cannot be changed.

## Phase 5 asset-management & rights-provenance contract (M2.0 — contract foundation only)

Purpose: define the **stable, versioned** shapes for an asset, its rights record, and its binding to an approved scene, so the future Phase 5 asset service (M2.1+) can be built against a fixed schema. **M2.0 is a contract only**: `contracts/assets.py` runs no network call, touches no database, imports nothing from TTS/alignment/FFmpeg/render, downloads/ingests no bytes, defines no route, and assigns no asset to a real scene. Asset storage, SSRF-guarded fetch, the approval ledger, persistence, routes, and export-readiness gating are later milestones (M2.1+), **explicitly not in M2.0**. Reuses `StrictModel`/`digest`/`canonical` from `contracts/evidence.py` (no parallel contract style); the **M0 scene contract is not modified**.

**Three boundaries:**
- **Asset descriptor** — `AssetDescriptorV1` (`defence-studio.asset-descriptor.v1`, strict): stable identity (`asset_id`, a 64-hex content-digest basis so byte-identical descriptors dedup), `job_id`, `kind` (`image`/`footage`/`audio`/`music`/`graphic`/`map`/`document`/`other`), `title`/`description`, content integrity (`AssetContentV1`), provenance (`AssetProvenanceV1`), an optional `rights` record, and a `review_status`. **Ingestion is never approval:** `review_status` defaults to `DRAFT`, and an `APPROVED` descriptor must carry a rights record.
- **Rights record** — `RightsRecordV1` (`defence-studio.asset-rights.v1`, strict): `rights_basis` (`creator_owned`/`licensed`/`public_domain`/`cc_by`/`cc_by_sa`/`cc_by_nc`/`official_release_permitted`/`fair_use_claimed`/`unknown`), `licence_id`/`licence_name`/`licence_url`, `attribution_required` + verbatim `attribution_text`, `permitted_uses` (`broadcast`/`web`/`derivative`/`thumbnail`), `commercial_use` (`allowed`/`prohibited`/`unknown`), bounded free-text `restrictions`, and `expires_at`. These are **operator assertions reviewed by a human**, kept distinct from source-provided facts — a reachable licence URL does not make the terms true, and public accessibility never implies reuse rights.
- **Scene assignment** — `AssetAssignmentV1` (`defence-studio.asset-assignment.v1`, strict): a *separate, versioned* artifact binding one `asset_id` to one `scene_id` of an **approved** scene plan, pinned to the exact `scene_plan_sha256` + `scene_plan_version` (+ `language`, `version`, `created_at`, optional `target_use`) and the `effective_rights` verdict recorded at assignment time. Kept entirely separate from M0's `VisualSuggestionV1` (a non-binding idea, explicitly *not* an assignment) so assets can be assigned/replaced without rewriting the plan or script. A service re-derives the verdict and enforces a stale-plan 409; the contract guarantees the binding fields are present and well-formed.

**Content integrity (no fabricated hashes).** `AssetContentV1` carries a `ContentStatus` (`REFERENCED_ONLY` default / `MEASURED` / `UNAVAILABLE`). A `content_sha256` (64-hex) **and** a verified `byte_size` may appear *only* with `MEASURED` (real bytes stored + hashed by a later milestone); a referenced-only asset carries neither — never a guessed digest. Declared provenance text (`source_title`/`creator`/`publisher`) uses `DeclaredText` with a `MetadataFactStatus` (`COLLECTED`/`UNAVAILABLE`/`NOT_COLLECTED`, mirroring F3's `MetadataStatus`): a `COLLECTED` field must carry a non-empty value and a non-collected field cannot smuggle one in — source facts are never fabricated.

**Deterministic fail-closed rights gate.** `evaluate_effective_rights(rights, provenance, *, now_iso=None, for_commercial=True, target_use=None)` is pure (no network, no implicit clock) and yields an `EffectiveRights` verdict — the only `CLEAR` state may appear in an approved commercial export; everything else is a specific blocker: no rights record / unknown basis / unknown commercial-use / no usable provenance → `UNVERIFIED`; a past `expires_at` (vs the caller-supplied `now_iso`; a malformed expiry fails closed) → `EXPIRED`; commercial render with `cc_by_nc` or `commercial_use=prohibited` → `BLOCKED`; a `target_use` outside the declared `permitted_uses` → `RESTRICTED`; otherwise `CLEAR`. (The CC-BY-NC rule mirrors the project's existing treatment of the non-commercial alignment-model blocker.)

**Validation / integrity.** `extra="forbid"` + `strict=True` reject any unknown field and loose coercion across every model; all hashes are 64-hex (lowercase); `schema_version` literals are pinned; `permitted_uses` carry no duplicates; `restrictions` are non-empty and bounded; `attribution_text` without `attribution_required` is rejected. `asset_digest`/`rights_digest`/`assignment_digest` are the canonical-JSON content hashes (same `canonical`/`digest` as evidence/scene artifacts) — identity-stable and input-key-order-independent, for a future service to bind approval/dedup to.

**Phase 5 boundary** — `contracts/assets.py` imports only `contracts/evidence.py` (`StrictModel`/`digest`); nothing from the scene plan module, TTS/alignment/FFmpeg/render, no route, no DB, no provider, no byte I/O. The deliverable is a fixed asset/rights/assignment schema consumable by M2.1+ without changing this module or M0.

**Tests**: `tests/test_asset_contract_m2_0.py` (20, contract-only — no network, no DB, no service) — valid asset/rights/assignment shapes; missing/malformed hashes and the MEASURED-only content-hash rule (no referenced-only fabricated digest); `DeclaredText` collected-vs-fabricated/blank rejection; the deterministic rights gate across unknown/missing-provenance (`UNVERIFIED`), `cc_by_nc`/prohibited (`BLOCKED`, allowed for a non-commercial render), target-use-outside-permitted (`RESTRICTED`), past/malformed expiry (`EXPIRED`), and fully-specified (`CLEAR`); attribution-without-requirement rejection; duplicate permitted-use and empty/oversized restriction rejection; ingestion-is-not-approval (APPROVED requires rights); assignment binding to the exact plan hash/version/scene_id and language/field validation; deterministic key-order-independent digests; and strict rejection of unexpected fields + wrong schema-version literals everywhere. Full backend suite re-run once after: **242 passed, 2 skipped** (F3's opt-in live-provider checks), up from 222; no prior test modified. (M2.1 service implemented below; see next section.)

## Phase 5 asset-management & rights-provenance service (M2.1 — reference-only)

Purpose: turn the M2.0 contracts into a working, human-paced service — register reference-only assets, attach immutable rights revisions, deterministically re-evaluate effective rights, assign an asset to a scene of an **approved** scene plan, and record an auditable human rights decision. Synchronous HTTP under `/api/jobs/{job_id}/assets/*` + `/scenes/{scene_id}/assets` + `/assignments[/readiness]`, like F5/Phase 2/3/M1. **Reference-only: no byte download, no provider fetch, no SSRF surface** — an asset is a URL/reference until a later, separately-authorized milestone measures it.

**Single engine, reused.** `services/assets.py::AssetService` subclasses `SceneService` (→ `ScriptService` → `EvidenceService` → `ReviewService`), reusing job-ownership checks, the `ArtifactStore`, the note/idempotency-key validators, JSON-artifact integrity reads, and the approved-scene-plan accessor (`scene_plans WHERE status='APPROVED'`). The `Asset*` exceptions derive from the `ReviewError` family, so the **existing** handler maps 404/409/422 with no new handler. Assignment reads the M1-owned `scene_plans` table read-only; **M1 is not modified**.

**Registration (reference-only, dedup, never approval).** `register_asset` computes `asset_id = asset_digest(body-without-id)` so byte-identical descriptors dedup; persists the canonical descriptor bytes under `jobs/<job>/assets/<asset_id>.json` + an `assets` row at `review_status=DRAFT`, `content.status=REFERENCED_ONLY`. Idempotent by `(job_id, Idempotency-Key)`; a second byte-identical descriptor under a new key dedups to the same row.

**Rights revisions + deterministic re-evaluation (never trusts a stored verdict).** `set_rights` validates a `RightsRecordV1`, stores an immutable `asset_rights` revision, and **re-derives** `effective_rights` via the pure `evaluate_effective_rights` predicate (unknown basis / unknown commercial-use / missing provenance → `UNVERIFIED`; `cc_by_nc`/prohibited for a commercial render → `BLOCKED`; past/malformed expiry → `EXPIRED`; target-use outside permitted → `RESTRICTED`; else `CLEAR`). Changing rights invalidates a prior `APPROVED` (back to `PENDING_REVIEW`) because the reviewed rights changed. The verdict is re-derived at register/set-rights/assign/review/read time, never read back from a client-supplied value.

**Assignment pinned to the exact approved plan.** `assign_asset` (in `BEGIN IMMEDIATE`) reads the current **APPROVED** scene plan; no approved plan → `AssetStaleRevision`/409; an unknown `scene_id` → `AssetValidationError`/422; an asset whose re-derived verdict is not `CLEAR`/`RESTRICTED` is refused (unknown/expired/blocked fail closed). The stored `AssetAssignmentV1` is pinned to the plan's exact `scene_plan_sha256` + `scene_plan_version` + `scene_id`. Idempotent by `(job, language, Idempotency-Key)`. `list_assignments` flags `stale_plan` when the current approved plan hash differs (a later plan re-approval is detectable). `remove_assignment` deactivates an assignment without rewriting the plan or script and never re-approves rights.

**Human review + append-only audit (pinned digests + optimistic concurrency).** `review_asset` (in `BEGIN IMMEDIATE`) pins the decision to the exact `reviewed_asset_sha256` + `reviewed_rights_sha256` the reviewer saw (mismatch → `AssetStaleRevision`/409) and to `expected_revision` (mismatch → `AssetRevisionConflict`/409); a duplicate `(asset, reviewer, Idempotency-Key)` replays; the current `asset_reviews` upsert and the append-only `asset_review_history` row are written in the **same transaction**. An `APPROVED` decision is refused unless the re-derived verdict is `CLEAR`/`RESTRICTED`. Decisions: `APPROVED`/`REJECTED`/`RESTRICTED`/`CHANGES_REQUESTED`.

**Readiness gate (read-only, specific blockers).** `assignment_readiness` lists, per approved-plan scene, specific blockers: no asset assigned, `STALE_PLAN`, missing descriptor, effective rights not `CLEAR`, or rights not `APPROVED`. A precursor to the Phase 8 QC rights check; changes no state.

**Persistence (schema v6→v7, `database.py::_upgrade_v6_to_v7`, additive).** Five tables separating immutable content-addressed records (`assets`, immutable `asset_rights` revisions, versioned `asset_assignments`) from the append-only rights-approval ledger (`asset_reviews` current + `asset_review_history`). No F1–M1/evidence/script/scene table touched; DDL + version bump commit/roll back together inside `BEGIN EXCLUSIVE`; accepted prior versions `{1,2,3,4,5,6,7}`; unsupported versions fail closed. Stored artifact paths use bounded hash-prefix filenames (full hashes live in the DB rows) to stay well under Windows MAX_PATH.
