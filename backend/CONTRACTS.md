# Defence Studio component contracts

F1 job and artifact contracts below remain in effect. F2 worker scheduling and recovery are defined in [`WORKER_CONTRACT.md`](WORKER_CONTRACT.md); its SQLite schema is version 2 and its API addition is `POST /api/jobs/{job_id}/queue`. F3 content acquisition is defined below under "F3 content acquisition contract" and runs only as a registered handler for the `topic_search_and_source_collection` worker stage. F4 source analysis is defined below under "F4 analysis contract" and runs only as a registered handler for the `extraction_validation_normalization_deduplication` worker stage.

## JobCreateV1 — `defence-studio.job-create.v1`

Purpose: persist the initial owner-scoped workflow request. Required fields: `topic` (trimmed, 1–1000 chars), `language` (trimmed, 1–1000 chars; API constrains to 2–20). Idempotency key is an HTTP header, 1–200 chars. Owner identity is derived from a verified HS256 bearer token's string `sub`, never from the request body. Output is JobStateV1, including stable UUID `job_id`, lifecycle status, ordered stages, and artifact references.

Validation: missing/oversize input → 422; no/invalid/expired token → 401; key reused for a different normalized request → 409. Same owner/key and same payload returns the original job. One `BEGIN IMMEDIATE` transaction plus UNIQUE(owner_id, idempotency_key) prevents duplicate rows under concurrent requests. Job creation persists the thirteen stage references from the locked design order; it does not schedule execution.

## Stage transition

Input: job ID, stage key, destination status, optional error up to 4000 characters. Statuses: PENDING, RUNNING, AWAITING_REVIEW, COMPLETED, FAILED, SKIPPED. From PENDING: RUNNING or SKIPPED. From RUNNING: AWAITING_REVIEW, COMPLETED, FAILED. From AWAITING_REVIEW: RUNNING, COMPLETED, FAILED. From FAILED: RUNNING. COMPLETED and SKIPPED are terminal. FAILED requires an error. A stage entering RUNNING or SKIPPED must have its predecessor COMPLETED or SKIPPED. Owner mismatch is intentionally indistinguishable from missing job (404).

Each valid transition increments the stage version and appends a transition record with UTC timestamp and error. The job updated timestamp and derived status persist in the same transaction. Invalid transition is 409; malformed status/error is 422. No worker side effect occurs.

## ArtifactReferenceV1 — `defence-studio.artifact-reference.v1`

Fields: artifact type, owning stage key, positive per-job/type version, relative URI under `jobs/<job_id>/`, lowercase SHA-256 digest, schema version, stable artifact ID and creation timestamp. The stage must have started. Each registration appends a version; prior versions remain addressable. Unknown stages, unsafe/out-of-job paths and invalid hashes are rejected. This boundary stores references and a claimed digest; it does not write files, verify bytes, or establish media rights.

## F1 persistence and failure behavior

SQLite is the only F1 authority. F1 initially used `schema_info` version 1 with foreign keys, WAL and 30-second busy timeout. F2 migrates it additively to version 2 for persistent scheduling, claims and recovery. Unsupported versions fail closed before application-table DDL. SQLite busy timeout/transactions bound ordinary contention. Unexpected database errors propagate as server errors; changes before commit roll back when the connection closes.

## HTTP endpoints

`POST /api/jobs`; `GET /api/jobs/{job_id}`; `POST /api/jobs/{job_id}/stages/{stage_key}/transitions`; `POST /api/jobs/{job_id}/artifacts`; and owner-authenticated `POST /api/jobs/{job_id}/queue`. All require a trusted issuer's HS256 token using the configured server secret, with `sub` and `exp`. Defence Studio does not mint tokens, register users, rotate/revoke tokens, or connect to an existing auth server. Components: `contracts/jobs.py`, `database.py`, `repositories/jobs.py`, `services/jobs.py`, `services/worker.py`, `auth.py`, `api/app.py`. Automated tests: `tests/test_workflow_jobs.py` and `tests/test_worker_engine.py`.

## F2 worker and claim contract

Only an owner can queue their new draft job; duplicate queue requests do not create another dispatch. Workers claim the first eligible stage in the locked order using SQLite `BEGIN IMMEDIATE` and a unique active-claim index. Claim IDs and worker IDs persist. Heartbeats and result commits are fenced by claim identity and an unexpired lease. Expired claims become failed attempts and retry after persisted exponential backoff until the three-attempt default is exhausted; exhaustion is terminal. Startup recovery runs with API lifespan startup. The API does not start a worker or register stage handlers. External side effects require stage idempotency keys or reconciliation; arbitrary exactly-once behavior is not claimed. Full lifecycle, schema, and shutdown rules are in `WORKER_CONTRACT.md`.

## F3 content acquisition contract

Purpose: acquire real source bytes for an approved research request and preserve traceable provenance, without starting extraction, verification, or any downstream phase. F3 runs only inside the F2 durable worker as the handler registered for the locked stage `topic_search_and_source_collection` (`defence_studio.contracts.acquisition.ACQUISITION_STAGE`); it has no HTTP endpoint and no synchronous execution path.

**AcquisitionRequestV1** (`defence-studio.acquisition-request.v1`, `defence_studio/contracts/acquisition.py`) — the stage's *input* artifact, produced by the predecessor stage and consumed from `context.input_artifacts` by `artifact_type == "acquisition_request"`. Fields: `job_id`; `targets` (non-empty list of `AcquisitionTarget`: `target_id`, `url`, `method` in `("auto","http_page","youtube_subtitles")`, `language_preferences`, optional `title_hint`); optional `project_id`; `limits` (`AcquisitionLimits`: `max_bytes_per_source`, `timeout_seconds`, `max_sources`, `max_redirects` — clamped server-side to hard ceilings in `acquisition/service.py`, never widened by the request). `defence_studio.contracts.acquisition.request_from_dict` parses and validates this; malformed input raises `RequestValidationError`, which the handler turns into a closed stage failure rather than guessing a default.

**AcquisitionResultV1** (`defence-studio.acquisition-result.v1`) — the stage's *output*, written as one JSON manifest artifact (`artifact_type = "acquisition_manifest"`, URI `jobs/<job_id>/research/acquisition_result.json`) referencing the hash of the exact bytes written. Carries `requested`/`succeeded`/`failed`/`skipped_duplicate` counts and one `AcquiredSourceV1` per target: `source_id` (stable SHA-256-derived dedup key over the canonical URL), `status` (`ACQUIRED`/`FAILED`/`SKIPPED_DUPLICATE`), `declared_metadata` (title/publisher/published_at/language, each paired with a `MetadataStatus` of `COLLECTED`/`UNAVAILABLE`/`NOT_COLLECTED` so "the source didn't supply this" is never conflated with "we didn't check"), `artifacts` (one `ArtifactRef` per stored file: type, relative URI, SHA-256 of the actual bytes, byte count, media type), `original_metadata` (raw provider-reported fields), `provenance` (provider name/version, source component, requested/canonical/final URL, acquisition timestamp, originating `target_id`), and on failure an `AcquisitionError` (`code`, `message`, `retryable`). A target never silently becomes a different source: failure is reported as `FAILED` with an honest error, not a substitution.

**Security boundary** — `defence_studio/acquisition/url_guard.py`'s `UrlGuard` rejects non-http(s) schemes, embedded credentials, and any URL whose host resolves to a loopback/private/link-local/reserved/multicast/unspecified address (including IPv4-mapped/6to4/Teredo IPv6 forms), blocking on *any* resolved address to defeat split-horizon DNS. `defence_studio/acquisition/http_client.py`'s `GuardedFetcher` re-validates every redirect hop through the same guard (closing redirect-to-SSRF), bounds redirects, streams the body with a hard byte ceiling enforced against both a declared `Content-Length` and the actual stream, and sends no cookies/Authorization/credential headers. Residual risk — DNS can change between validation and connect (TOCTOU) — is documented in that module's docstring, not claimed solved; full mitigation needs network egress controls around the worker host.

**Storage boundary** — `defence_studio/storage/artifacts.py`'s `ArtifactStore` is the only writer of acquisition bytes. Every URI must resolve under `jobs/<job_id>/...`, rejecting backslashes, absolute paths, `.`/`..` segments, and any resolved real path outside the job directory (defence-in-depth against symlink tricks). Writes are atomic (`tempfile` + `os.replace`) so an interrupted write never leaves a half-written file for a later SHA-256 to trust. `safe_filename` caps generated filenames at 80 characters with a content-hash fallback stem, avoiding the Windows `MAX_PATH` failures QVault's acquisition storage previously hit on long URL slugs.

**Providers** (`defence_studio/acquisition/providers/`) — `http_page` (generic `fallback=True` provider; downloads any http(s) page/PDF through the guarded fetcher, detects PDF-vs-HTML by content, and extracts only `<title>`/`og:site_name`/`article:published_time`/`html[lang]` as *declared* metadata — no article-body extraction, no OCR) and `youtube_subtitles` (host-restricted to YouTube domains; downloads *subtitles/captions only*, never the video stream, via an injectable yt-dlp backend that fails closed with a clear message if yt-dlp is not installed — the `youtube` extra is optional). `AcquisitionProvider.supports()`/`fallback` let `ProviderRegistry.resolve()` pick a provider under `method="auto"` by preferring any specific provider over a fallback; an explicit `method` pins one provider and raises `method_mismatch` rather than silently acquiring something else.

**Idempotency and reuse** — `AcquisitionService` derives `source_id` deterministically from the canonical URL, skips in-request duplicates as `SKIPPED_DUPLICATE`, and before any network call checks a per-source `acquired.json` sidecar; if its referenced artifact(s) still exist and hash-match, acquisition is skipped entirely and the prior artifacts are reused (verified in `test_acquisition_service.py::test_idempotent_reuse_avoids_redownload` and exercised across a real claim-expiry retry in `test_acquisition_handler.py::test_retry_through_worker_reuses_artifacts_without_redownload`). A handler re-run after a crashed attempt (lease expiry) therefore does not re-download.

**Partial success** — one target's failure never aborts the others; `AcquisitionResultV1.succeeded`/`failed`/`skipped_duplicate` and each source's own `status` make partial outcomes explicit rather than collapsing a multi-target request into one pass/fail.

**Tests**: `tests/test_url_guard.py`, `tests/test_artifact_store.py`, `tests/test_acquisition_service.py` (provider behavior via `httpx.MockTransport` and an injected yt-dlp double — the adapter boundary, not a live network claim), `tests/test_acquisition_handler.py` (full run through the real F2 `Worker`, a fail-closed missing-request case, retry-with-reuse across simulated lease expiry, and cross-owner artifact-read denial), and the opt-in, skipped-by-default `tests/test_integration_live.py` (real network; gated by `DEFENCE_STUDIO_LIVE_HTTP=1` / `DEFENCE_STUDIO_LIVE_YOUTUBE=1`).

## F4 analysis contract

Purpose: convert the real bytes F3 acquired into structured, traceable research material for the later human-review phase, without asserting that any extracted claim is true. F4 runs only inside the F2 durable worker as the handler registered for the locked stage `extraction_validation_normalization_deduplication` (`defence_studio.contracts.analysis.ANALYSIS_STAGE`); it has no HTTP endpoint. Its predecessor is `topic_search_and_source_collection` (F3), one ordinal earlier in the locked stage order.

**AnalysisRequestV1** (`defence-studio.analysis-request.v1`, `defence_studio/contracts/analysis.py`) — logical input shape: `job_id`, `owner_id`, the predecessor's `acquisition_result_uri`/`acquisition_result_sha256`, optional `topic`, and `AnalysisLimits` (`max_sources`, `max_bytes_per_source`, `max_text_chars`, `max_claims_per_source`, `near_duplicate_threshold`, `min_claim_chars`, `max_claim_chars` — clamped server-side in `services/analysis.py::_hard_limits`, never widened). In the worker path, the handler (`make_analysis_handler`) derives this directly from `context.input_artifacts`: it locates the artifact whose `artifact_type` equals `ACQUISITION_RESULT_ARTIFACT` — the same string as F3's real `defence_studio.acquisition.handler.ACQUISITION_MANIFEST_ARTIFACT_TYPE`, `"acquisition_manifest"` — among all completed-predecessor-stage artifacts the worker gathers (not only the immediate predecessor), and fails closed with `AnalysisInputError` if none is present.

**Input verification** — before any byte is read, `AnalysisService._load_acquisition` confirms the manifest artifact exists, re-computes its SHA-256 and compares it against the reference hash the worker claim carries (an independent integrity check, not a trust-on-read), and parses it as JSON. Any mismatch, missing file, or malformed JSON raises `AnalysisInputError` rather than fabricating a manifest. Per source, before normalizing: the chosen byte artifact's URI is resolved through the same path-containment guard as F1/F3 (`ArtifactStore._resolve`, rejecting traversal/absolute/backslash paths), its declared byte count is checked against `max_bytes_per_source`, its bytes are read with a hard size cap, and the actual SHA-256 of what was read is compared against the manifest's recorded hash — a mismatch is `ARTIFACT_CORRUPT`, not a lower-confidence pass-through.

**NormalizedSourceV1** (`defence-studio.normalized-source.v1`) — one per acquired source, `status` `NORMALIZED` or `FAILED`. Carries the detected language (a conservative Tamil-vs-Latin script heuristic, `ta`/`en`/`und` — not full language identification), the normalized text and its own SHA-256/char count, the verified `OriginalArtifactRef` (type/uri/sha256/bytes/media_type of the exact bytes normalized), an explicit `original_sha256_verified` flag, separated `SourceDates` (`published_at` only when F3 marked it `COLLECTED`, vs. `acquired_at`), and per-source warnings. Normalization (`defence_studio/analysis/normalize.py`) dispatches on media type: HTML (script/style stripped, block tags become paragraph breaks, entities decoded), WebVTT/SRT (cue text joined with preserved per-cue start/end timestamps and character offsets), and plain text/JSON (whitespace/Unicode NFC cleanup only). Unsupported media types or undecodable bytes raise `NormalizationError`, recorded as a `FAILED` source with an honest reason — never a fabricated transcript. Whitespace/boilerplate/markup is removed; qualifiers, negations, numbers, units, dates and designations are never touched by normalization.

**Deduplication** (`defence_studio/analysis/dedup.py`) — produces `DuplicateGroupV1` records with an explicit `basis`: `SAME_CANONICAL_URL` (the same URL acquired more than once), `IDENTICAL_CONTENT_HASH` (byte-identical normalized text from different URLs — syndication), or `NEAR_DUPLICATE_TEXT` (token-4-shingle Jaccard similarity at/above the configurable, tested `near_duplicate_threshold`, default `0.82`). Every original source record is preserved regardless of grouping; grouping never deletes or merges a source, and similarity is never treated as independence or as proof a claim is true. Independent sources merely discussing the same subject with different wording fall below the threshold and are deliberately left ungrouped.

**ExtractedClaimV1** (claim extraction in `defence_studio/analysis/claims.py`) — `claim_text` is always a verbatim sentence span from the normalized text (never paraphrased), with an `EvidencePassageV1` giving exact `start_offset`/`end_offset` (and, for subtitle sources, the covering cue's `timestamp_start`/`timestamp_end`). A candidate sentence is only extracted if it carries at least one detected factual signal (a quantity, date, designation, or named token) via conservative regex detectors; qualifiers (`reportedly`, `according to`, `estimated`, …) and negation are detected and recorded on the claim rather than removed, and `CandidateEntities` keeps designations/quantities/dates as deterministically matched substrings, not a typed NER classification F4 does not attempt. No AI model is invoked for this: `extraction_method` is always `"deterministic-sentence-span"` and `extractor_version` is a fixed constant, not a model name.

**Claim relationships** (`defence_studio/analysis/relationships.py`) — `ClaimGroupV1` groups claims with identical or near-duplicate text (entity-subject-blocked for cost, never all-pairs), always carrying the note that this is a textual relationship only, not corroboration. `ClaimConflictV1` flags same-subject claim pairs from *different* sources with opposite negation or mismatched quantities, always `flagged_for_review=True`; conflicting claims are never merged, resolved, or dropped — both sides remain in `AnalysisResultV1.claims`.

**AI-output validation seam** (`defence_studio/analysis/ai_schema.py`) — F4 calls no AI provider; this module exists only so a future AI-assisted extractor's output is forced through `validate_ai_payload`, which requires a list of objects each with a non-empty `claim_text`, in-range non-inverted integer `start_offset`/`end_offset`, a list-of-strings `qualifiers`, and a boolean `has_negation`. Any malformed item raises `AiOutputError` and the **whole** payload is rejected — one bad claim is never silently dropped while the rest are accepted as partial evidence.

**AnalysisResultV1** (`defence-studio.analysis-result.v1`) — the stage's output artifact (`artifact_type = "analysis_result"`, URI `jobs/<job_id>/research/analysis/<input_digest>.json`), carrying `normalized_sources`, `duplicate_groups`, `claims`, `claim_groups`, `conflicts`, `warnings`, `failures`, source/claim counts, `status` (`COMPLETED` or `COMPLETED_WITH_FAILURES`), and `AnalysisVersions` (normalizer/extractor/dedup version strings). `input_digest` is a SHA-256 over the acquisition hash, each normalized source's identity, and the processor versions/limits — it is both the artifact's filename and (via `run_and_store`'s check-before-write) the idempotency key: re-running over unchanged inputs reuses the existing artifact instead of rewriting it. (During F5's prerequisite review this guarantee was briefly observed broken by a wall-clock-timestamp bug, and a separate gap in `ARTIFACT_UNREADABLE` reporting was also observed; both were fixed before F5 was built — see "F4 implementation and verification" in `project_status.md` for the fix. F5 still pins every review decision to the job's current artifact SHA-256 at decision time rather than assuming any F4 output is permanently immutable across future reruns.)

**Durability** — the handler (`make_analysis_handler`) is retry-safe under the F2 contract (register it with `retry_safe_stages={ANALYSIS_STAGE}`) because its output is deterministic and content-addressed as above, writes are atomic through the existing `ArtifactStore`, and a failed/interrupted attempt commits nothing (fenced by F2) so the next attempt simply recomputes the same result. A missing or integrity-check-failing manifest raises `AnalysisInputError`, which the worker records as a durable stage failure under F2's existing retry/terminal policy; per-source problems (unsupported media type, corrupt/unreadable bytes, failed normalization) are recorded as `ProcessingFailure` entries and do not abort the other sources.

**Tests**: `tests/test_analysis_f4.py` — valid-artifact processing with full provenance/traceability, missing/malformed/unsupported/corrupted-artifact handling, exact and identical-content duplicate detection, near-duplicate grouping without merging independent sources, qualifier/negation/date/quantity/designation preservation, claim-to-passage offset traceability, cross-source conflict flagging without merging, malformed-AI-output rejection, repeat-processing idempotency, interrupted-processing retry through the real F2 `Worker` without a duplicate artifact version, cross-user rejection, and one end-to-end test that runs the real F3 `build_acquisition_handler` (via a mocked HTTP transport) feeding directly into the real F4 handler, both driven only by the F2 worker. All 21 pass as of F5's full-suite run.

## F5 evidence review contract

Purpose: record explicit, authenticated, auditable human decisions over F3/F4 output. F5 is an evidence-review boundary, not automatic fact-verification — it never mutates an acquisition/analysis artifact and never asserts a claim is true. Unlike F3/F4, F5 has synchronous HTTP endpoints, because review is a human-paced action rather than a durable background stage.

**ReviewDecisionRequestV1 / ReviewDecisionRecordV1 / ReviewHistoryEntryV1** (`defence-studio.review-decision.v1` / `defence-studio.review-history.v1`, `defence_studio/contracts/review.py`) — a decision is `APPROVED_FOR_USE`, `REJECTED`, `NEEDS_MORE_EVIDENCE`, or `CONFLICT_UNRESOLVED` against either a `CLAIM` or a `SOURCE`, pinned to `reviewed_artifact_sha256` (the exact `analysis_result`/`acquisition_manifest` bytes the reviewer saw) and `expected_revision` (optimistic concurrency). All four decisions are reachable from any other decision or from no prior decision — the enforced constraint is revision-exactness and concurrency, not a restrictive state graph (see the module docstring for the rationale, including what `APPROVED_FOR_USE` does and does not authorize).

**Persistence** (SQLite schema v3, `database.py::_upgrade_v2_to_v3`) — additive-only `claim_reviews`/`source_reviews` (current decision, one row per `(job_id, claim_id|source_id)` `PRIMARY KEY`) and `claim_review_history`/`source_review_history` (append-only; `UNIQUE(job_id, subject_id, reviewer_id, idempotency_key)` makes a duplicate submission idempotent rather than a second audit row). No F1–F4 table, column, or row is touched; a decision references `job_id` (FK to `workflow_jobs`) and an opaque `claim_id`/`source_id` string validated against the *current* artifact's content at decision time — not a duplicate identity system.

**Service rules** (`services/review.py::ReviewService`) — every call verifies job ownership first (404-equivalent on mismatch, same as every other boundary). `decide_claim`/`decide_source` run inside one `BEGIN IMMEDIATE` transaction: replay of the same `(subject, reviewer, Idempotency-Key)` returns the existing record unchanged; `reviewed_artifact_sha256` not equal to the job's current artifact → `StaleRevision` (409); `expected_revision` not equal to the current stored revision → `RevisionConflict` (409, prevents a concurrent decision from being silently overwritten); unknown decision value or unknown `claim_id`/`source_id` against the current artifact → `ReviewValidationError` (422). `list_claims`/`list_sources` are read-models that merge the latest `analysis_result`/`acquisition_manifest` artifact with current review state, exposing `has_conflict`, `duplicate_groups`, and `is_stale` (a stored decision's SHA-256 no longer matching the current artifact) without ever resolving a conflict or merging a duplicate automatically.

**HTTP endpoints** — `GET /api/jobs/{job_id}/review/sources[?status=]`, `GET .../sources/{source_id}`, `GET .../sources/{source_id}/history`, `POST .../sources/{source_id}/decisions` (requires `Idempotency-Key`); claim equivalents under `.../review/claims[?status=&conflict=&source_id=]`. All require the same HS256 bearer token as every other endpoint. `create_app()` gained an optional `storage_root_path` parameter (defaults to `config.storage_root()`) so tests/deployments can point the review service's artifact reads at an isolated directory, mirroring the existing `database_file` override.

**Frontend** — `frontend/` is a new, framework-free static app (plain HTML/CSS/ES modules, no build step) served by FastAPI via `StaticFiles` mounted at `/` (registered after all `/api/...` routes so it never shadows them). This is the first UI Defence Studio has; see `component_registry/REGISTRY.md` for the primitives it introduces (status badge, confirm dialog, text field) and `project_status.md` for the manual mobile-Chrome verification still outstanding.

**Tests**: `tests/test_review_f5.py` — decision creation/retrieval, invalid decision/unknown-subject rejection, cross-owner denial, stale-revision rejection, optimistic-concurrency conflict, idempotent replay, append-only history ordering, conflicting-claim/duplicate-source surfacing and filtering, schema v2→v3 migration against a reconstructed real legacy database (preserving an existing job row), unsupported-version fail-closed, persistence across a fresh service instance (simulated restart), and API-level auth/stale/conflict/validation status codes via `TestClient`.
